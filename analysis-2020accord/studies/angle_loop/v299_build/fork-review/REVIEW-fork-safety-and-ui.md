# REVIEW: V299 fork commit, safety and UI lens

**Reviewer:** a subagent in the V299 fork round. It was read-only on the fork: no edits, no commits.
**Commit:** `66780911279bc5343406a042b173674feb3b1a81` on `Dom`, parent `2712e1336`, local and not pushed. The fork tree was clean before and after the review.
**Verdict: PASS_WITH_DEFECTS.** No defect found is a setpoint runaway or an un-overridable state that the code introduces. All the defects are LOW. Each one is a cosmetic or diagnostic issue, a documentation risk, or a class that predates this commit.

## What a FAIL would have looked like (written before the checks)
Any one of these would have been a FAIL:
- any latActive frame with |θ| ≤ 400° where |sp − θ| exceeds `error_max(v)`;
- the limiter seeded from a stale setpoint on a latActive rising edge;
- a non-latActive frame whose field is anything other than 0 or the wheel-angle hold;
- a panda or safety diff;
- a 0x1AB path that can move `canValid`;
- bar sign agreement below 0.85;
- the UI reading the status bits;
- `is_angle_fw` accepting A160, or rejecting a NUL-padded A16A or A16B;
- config A not restorable with the new keys;
- override references still live in the old test file.

## Defects (all LOW)

1. **The mici orange lane-line cue now fires on the opposite side from torque mode.** `model_renderer._get_ll_color` turns the left line orange when its filter is above 0.6. Under V295 torque mode the filter is `−actuators.torque`, which is positive for a right push, so a hard left turn lit the right line. The new feed `accord_eps_bar` is positive with left demand (it agrees with desired curvature 0.83 on segment 0, and with the angle bar 0.854), so a hard left turn now lights the left line. On V298 the cue never fired (torque was 0). The spec asked for this feed. The point is that the operator will see a mirrored cue compared with his last torque-mode drives. *Where:* `selfdrive/ui/mici/onroad/model_renderer.py:118-120`. *Fix:* if the operator wants the old side, feed `−accord_bar` to the mici filter only, or record the convention on the drive card.

2. **The sign label on `steeringTorqueEps` ("+ = left") is unverified.** The code chooses the sign so the bar matches today's drawing, and that part is right (0.854). The physical comments, however, say s10 "+ = right" and `steeringTorqueEps` "+ = left". The kit memory says the 427 tap's polarity is +sign(cmd), with cmd "+ = right". On segment 0, s10 agrees with desired curvature (+ = left) only 0.83, and with θ only 0.22. The labels are not proven either way (BELIEF). Today only the bar reads `steeringTorqueEps` on this car (grep), so nothing acts on it. A future consumer, or a kit decoder that reads `cs_tqeps` as before, would inherit an unproven sign. *Where:* `values.py:81-82`, `carstate.py:24,389`. *Fix:* mark the label as BELIEF in the comments, or prove it on a V299 drive (s10 against the angle error sp − θ during a hands-off hold).

3. **`ANGLE_STATUS_RATE` (bit 4) misses the lateral-accel clip.** The bit tests `|desired − angle_last| > min(jerk delta, MAX_ANGLE_RATE)`. When `get_max_angle_vm` (3.589 m/s²) binds, neither bit 4 nor bit 16 is set. This affects diagnostics only. *Where:* `carcontroller.py` `_update_angle`. *Fix:* set a reserved bit (for example 8) when `np.clip(..., ±max_angle)` changes the value, or document the gap.

4. **The EPS bar is not zeroed while lateral is off.** The old angle branch drew 0 when `!latActive`. The new branch draws the EPS lane torque whenever it is fresh, including in the request-off hold (ARM = 2, where the lane chases the wheel). The bar is drawn at reduced alpha then, so this is cosmetic. On a total CAN-feed stop the parser clock stops, and the bar holds its last value instead of zeroing; `canValid` and comm alerts dominate in that case anyway. *Where:* `torque_bar.py` `accord_eps_bar`. *Fix:* optional, return 0 when `!carControl.latActive`.

5. **Predates this commit (not V299): a non-finite `desired` angle crashes `card`.** `math.floor(NaN)` raises `ValueError` after `apply_angle_last` is set to NaN. The next latActive frames raise too, until lateral drops. The result is no 0xE4 frames, so the firmware's timeout path takes over. This is not a runaway. *Where:* `_update_angle`, raw line. *Fix:* if `desired` is not finite, treat the frame as hold (`desired = steering_angle`).

6. **Info only, not a defect: ClipScale 1.6 raises the P-demand cap against the hand.** At 1.6 the cap at ≤ 11.75 m/s rises from 26–40 % to about 42–64 % of the rail (values.py's s × clip: 52/64/33 counts per degree × 27.2/24.8/31.2°). With no fork override, more of it opposes the hand in the moderate band (refuter rev 2, item 7). Configs A, B and REVERT all ship scale 1.0, so this is not live. The kit's firmware-family convention also has a consequence: any EPS image whose header ends `A16<capital letter>` is treated as an angle image, so a torque image must never be headered that way.
