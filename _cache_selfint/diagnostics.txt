D5  WHICH SIDE OF THE TORSION BAR IS THE CAN ANGLE ON?
    The one structural question the whole analysis turns on, decided WITHOUT tau and
    WITHOUT any torque calibration -- from the roll-off of |Z| = |T / theta_dot| alone.

      sensor ABOVE the bar (wheel side):  T = -J*thddot - b*thdot exactly, so
                                          Z = -(j*w*J + b)  =>  |Z| MUST RISE, ~ w
      sensor BELOW the bar (pinion side): above the wheel-on-bar mode the wheel is
                                          pinned, Z -> +j*k/w  =>  |Z| MUST FALL, ~ 1/w
    13 -> 27.5 Hz is a factor 2.12 in w, so the two hypotheses predict 2.12 and 0.47.
    H1 is biased LOW by input noise and H2 HIGH by output noise; the truth is bracketed,
    so BOTH are shown and the conclusion must hold on both.

D6  WHAT A FEEDFORWARD theta_ddot CANCELLATION WOULD HAVE TO BE, and the correction it
    forces on docs/FEASIBILITY-SELF-INTERFERENCE-CANCELLATION.md section 3.4.

    The bar torque hands-off is EXACTLY the upper column's own free body:
        T_bar = -J*thddot_w - b*thdot_w                      (identity, not a model)
    but the firmware can only measure thddot_p, BELOW the bar (D5), and
        thddot_w / thddot_p = 1 / (1 - (f/fn)^2 + j*2*zeta*(f/fn))
    ⇒ a correct feedforward is NOT `gain * theta_ddot`.  It is `-J*theta_ddot` passed
      through a 2-pole resonant LOW-PASS at fn with the measured zeta -- i.e. a BIQUAD,
      i.e. a code cave, i.e. this kit's only bricking class.
