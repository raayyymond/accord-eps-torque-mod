Verifying the V0/V11 torque-mod plan in Ghidra (code.bin open, port 8193) overturned two load-bearing assumptions in `analysis-2020accord/TORQUE_MOD_V0.md` and sharpens [[reference-accord-demand-aggregator-pipeline]]. All instruction-verified this session.

**Mixer LKAS lane pinned [V].** Of the four ±0x2800 clamp blocks in mixer `FUN_00026c80`, the LKAS-torque lane is the **`0x27442` block** (clamps the `gp-0x3d8c` accumulator into `r26`). `r26` is preserved untouched to `0x277f2: mov r26,r6; sxh; jarl FUN_00042ac6` — it is the exact value handed to the gate. The other three blocks (`0x26ea0`, `0x26ec4`, `0x276de`) are NOT the LKAS lane. (Resolves the "CONFIRM LANE FIRST" open item in TORQUE_MOD_V0.md §3a-iii.)

**The shaper is a dual range-check, not a plain clamp [V].** TORQUE_MOD_V0.md modeled shaper `FUN_00042af8` as "clamp ±0x2000" and edited only `0x43b0e..0x43b1c`. But before that final clamp, `0x43ae0` reads `0xFEDF1502` (the gate output) and re-runs the **same plausibility idiom** the gate uses:
```
0x43ae8 addi 0x2800,r13,r8 ; 0x43aec addi -0x5001,r8,r0 ; 0x43af0 cmovc 0x0,r13,r12
```
`cmovc 0x0` -> anything outside ±0x2800 (including the gate's `0x7FFF` sentinel) **collapses to 0**. So overshooting the gate window does NOT add torque — it zeroes the LKAS command. This is the exact Civic V10A mechanism (a too-big command trips plausibility and kills LKAS). TORQUE_MOD_V0.md MISSED `0x43ae8/0x43aec`.

**Hard static-edit ceiling = ±0x3FFF (~2.0x) [V].** Both the gate `FUN_00042ac6` (`0x42ac6/0x42aca`) and the shaper input-check (`0x43ae8/0x43aec`) use `+0x2800 / -0x5001`. Widening the window to ±W requires 2nd immediate `-(2W+1)`; `W=0x4000` needs `-0x8001`, which **overflows signed imm16**. So `W=0x3FFF` (2nd imm `-0x7FFF=0x8001`) is the max. **TORQUE_MOD_V0.md §0/§4's "up to ~3.99x is a static value edit" is WRONG** — it considered only the int16 *storage* limit (0x7FFF), not the range-*check* idiom. **3x (24576) is a code rewrite** (restructure both comparison sequences), not a value edit.

**High-end binder RE-RESOLVED 2026-05-26 (Ghidra, full decompile of FUN_00042af8 + FUN_00043e44) — RETRACTS the earlier "motor current/thermal limiter" claim.** The operator correctly objected that the motor sources far more current for driver-assist than any LKAS command, so a thermal/I²t cap on LKAS makes no physical sense. It does not. The true high-end binder is a **DUAL-PATH LOCKSTEP REDUNDANCY MONITOR**:
- The LKAS torque demand is computed TWICE: once in the **integer** path (shaper `FUN_00042af8` → demand `gp-0x6b98`=0xFEDF1468) and once in a **parallel floating-point** path (`FUN_00043e44` → shadow `gp-0x6dbc`). A monitor (in BOTH functions) requires `|shadow*1024 − demand| ≤ ~5 counts` (the `+5U` makes the band symmetric); divergence sets fault bit `0x20`, summed with 6 sibling bits (gp-0x6db0/6db8/6dc0/6c84/3566 vs their int twins) into an accumulator that calls `FUN_0004613e(0x38c7,…)` / `FUN_000462e6(0x3f1b,…)` past 0x80/128.0.
- The ~8192 ceiling lives **identically in both pipelines**: INT = `clamp(±*(gp-0x4f64))` (0x43ae4 read, 0x43af6 `<0x2801` window-check) then `clamp(±0x2000)`; FLOAT = `clamp(±(gp-0x4f64)/1024 capped ≤10.0)` (0x4486e read, 0x4487e cap) then `clamp(±8.0)` (0x448c2/0x448ce; 8.0×1024=8192). The two were co-designed to agree at 8192. That agreement — not a motor limit — is why V11A/V12A (which raised only the INT static clamp) left the top at stock: the int gp-0x4f64 clamp still bound at ~8192 AND the float shadow still capped at 8.0, so raising one int clamp couldn't move the locked-together pair.
- `gp-0x4f64` IS still slewed by `FUN_0007b022` (calibration-driven dynamic torque-limit governor, inputs in the absent `0xF8000+` partition; NOT a provable I²t/thermal model — that label was over-read). But it is applied symmetrically in both paths; its exact value (~0x2000 inferred from road behavior, no bench read available) matters less than the lockstep structure.
**To raise the high end you must raise the ceiling in BOTH pipelines in lockstep** so the monitor still sees agreement — see [[project-accord-torque-mod-v0]] V13. Residual risk: the int and float paths must also agree within ±5 counts in the 8192→16383 region that was previously masked by saturation; float-vs-int rounding there is unverifiable without bench/emulation.
