**The leading root cause of V38's hard-turn ratchet.** Byte-verified 2026-07-20 in `FUN_0004503c` (`m_motor_torque_governor`), stock `code.bin`.

**The mechanism** (`0x454f8`-`0x45526`, writeback `0x455cc`):
- `cmp 0x4,r12` @`0x454fc` — compare is against literal **4**; `bne 0x455c4` skips substitution entirely otherwise.
- The comparison is on **ABS + clamped MAGNITUDE**, unsigned (`bnh` @`0x45526`): substitution runs only when `|fresh gp-0x6ace| > |previous gp-0x138a|`.
- The substituted value is **not a hard freeze** — it re-runs the same rate-interpolation block (cals `tp+0x7134`/`tp+0x748e`) that mirrors the primary computation at `0x4546a`-`0x454e4`, but seeded from the OLD value: "hold near the previous, rate-shaped."
- ⚠ **`0x455cc st.h r6,-0x138a[gp]` is an UNCONDITIONAL writeback.** The suppressed output becomes next cycle's comparison baseline ⇒ **cumulative and self-sustaining across consecutive state-4 cycles**, not a one-shot clamp.

**State 4 is reachable mid-drive, with no UDS session and no power cycle.** Of 5 `st.b 4,-0x67fa[gp]` sites image-wide, two are normal-mode: `0x19bb0` (**5→4**, when `gp-0x68ad == 0`) and `0x19e54` (**10→4**). The others are diag-only (`tp+0x74d0==4`) or the power-on reset `0x57e94`. This **refutes** the long-standing assumption that state 4 is one-time bring-up.

**The trigger is torque-sensor linked, which is why it shows on hard turns.** `gp-0x68ad`'s sole updater `FUN_0001a104` runs every cycle at the top of both the state-4 and state-5 handlers, and **no branch leaves it unchanged at 1** — it is either cleared unconditionally or passed to `FUN_00022016`, which preserves it only while `gp-0x679d==1` OR (`gp-0x6a5e != 0` AND `gp-0x67f4 == 1`) — nonzero voted column torque AND the voter plausibility latch converged. A column-torque zero crossing or a momentary plausibility drop near sensor saturation trips `5→4` on the next dispatch cycle.

**Why it only surfaced on V38.** The substitution caps the *increase*, so the felt severity is the shortfall `(demanded − held)`. Stock could demand at most 417 LKAS counts; V38 demands 1782 ⇒ the ratchet is ~4× deeper. The mechanism is old; the 4× raise made it perceptible. Consistent with [[reference-accord-gain-rescaling-invariance-partition]], which independently assigned the ratchet to "downstream of the gain, above 417 counts." It also explains why strong **driver** torque moves the wheel fast with no symptom — driver torque is mechanical and never passes through this governor.

**State 4 is a live operating condition, not a boot value:** specially handled in `FUN_00044cf0` @`0x44cfe` (state==4 **suppresses a torque-cap LERP branch** — an independent second torque-shaping effect), plus `FUN_0002cc2a`, `FUN_0002e734`, `FUN_00041304`. Separately `FUN_0003d04c` @`0x3d074` **rejects the LKAS deliver-commit outright (return 6) when state == 10.**

**V42 IS BUILT (2026-07-20, UNFLASHED) AND FIXES THIS WITH ONE BYTE** (V42 also carries a separate cal-only Change 2 targeting the vibration — see [[v42-state4-ratchet-and-r26-built]]). `0x454FE`: `0xBA -> 0xB5`, i.e. Bcond condition nibble `0xA (BNE) -> 0x5 (BR)`, so the substitution block `[0x45500,0x455C4)` becomes unreachable. Displacement untouched -> target stays `0x455C4`. No cave, no relocation, zero calibration edits; 5 bytes total incl. the `0xC4FFC` main-block CRC. **No cal lever exists** - all six entry-chain functions have zero `tp+` reads, and the branch decision itself reads no cal. Safety case: `FUN_00043e44` reads neither the state byte nor `gp-0x6ace`/`gp-0x138a`/`gp-0x4cca`; the `gp-0x4cca` shadow is written by the same instruction pairs on every path; and the one real monitor `FUN_0004595a` (no debounce, `FUN_00016de6(0x1d)`) sees, after the edit, exactly the value states 3/5/6/8/9/10/11 already produce - because the primary computation reads `gp-0x67fa` **zero times** and is therefore state-independent, and `gp-0x6ace` already holds it before the state-4 check. ✅ **That last point was UPGRADED TO A PROOF 2026-07-20.** The slew at `0x4543a`-`0x45458` is **asymmetric**, not a symmetric `[held±step]` clamp — it has two toward-zero fast paths (`cmp r0,r10 ; ble 0x45458` and `cmp r0,r10 ; bge 0x45458`) that snap straight to TARGET. All four branches give output ∈ {TARGET, min(TARGET,HELD+STEP), max(TARGET,HELD−STEP)}, so **`|output| ≤ |TARGET|` and signs agree in every branch**, for ANY held value. With `TARGET = clamp(gp-0x6b94, ±bound)` that is exactly `FUN_0004595a`'s two fault conditions ⇒ it **cannot trip on the primary path**. Under the symmetric reading it would NOT have held. ⚠ Standing fact (recorded, not gating): `FUN_00016de6(0x1d,…,1,1)` has **no debounce either** — one true condition reaches motor-off with no grace period. See `docs/handoffs/2026-07/HANDOFF-2026-07-20-v42-state4-ratchet.md`.

**How to apply:** state graph is `1→3→{4,6}`; `4→{11,10,6, or 5 iff gp-0x68ad==1}`; `5→{11 if ready, 4 if gp-0x68ad==0}`; `10→{6,4}`; `11→6`; `6→{7,9}`; `9→7`; `7` = dead-end sink. `{6,7,9}` is a one-way degraded branch. ⚠ **[OPEN] `gp-0x437c` vs `gp-0x4378`** (absolute `0xFEDF3C84`/`0xFEDF3C88`) gate the set/clear halves of `gp-0x68ad` asymmetrically and have **no `gp`-relative writer** — likely written via `ep` short-format `sst.w` (which will not appear in a gp-displacement operand search). If they are the same sticky flag, the SM bounces `5↔4` every cycle ⇒ deep persistent ratchet; if different, `5→4` is rarer. That question sets the ratchet's depth.
