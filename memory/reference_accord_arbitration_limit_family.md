> **⚠⚠ UPDATE 2026-05-26 (late):** the arb output `gp-0x6b3c` does NOT only feed a monitor — it reaches the motor via `limit_and_pack`→`distribute_clamp` (source idx 1)→mixer→`gp-0x6b4c`→`gp-0x6b94`→`gp-0x6ace`→`gp-0x6acc`→shaper→`gp-0x6b98`→FOC (xref-verified). The dominant high-end binder on the delivered (combined) command is the runtime governor `gp-0x4f64` = cal `tp+0x7202`=`0xC6202`=4762, not the arb output gain alone and not the ±0x2000 static. The arb gain (891) sets the LKAS *source's* magnitude (one of ~10 summed sources); the governor caps the sum. See [[reference-accord-lkas-delivery-and-governor]].
>
> **⚠ CORRECTION 2026-05-26 (eve) — the bottleneck chain below MISSED the real binder: the output GAIN.** Two fixes: (1) **`tp = 0xBF000`, not `0xF8000`** (application re-sets it @`0x140ce`; see [[reference-accord-databin-tp-base]]). (2) After the setpoint curve-limit, arbitration applies **`out = (demand × polarity[gp-0x6752] × GAIN) >> 15`, then clamps ±`arb_output_clamp`**, where **GAIN = `*(s16)(tp+0x746c)` = `0xC646C` = 891** and **`arb_output_clamp` = `*(u16)(tp+0x71b4)` = `0xC61B4` = 512**. At full command the curve-pinned demand (~15360) × 891 >>15 ≈ **±418** — *below* the 512 clamp — so **the GAIN (891), not the shaper ±0x2000, sets the LKAS high-end**. The ±0x4000 / curve-15360 / ±0x2800 / ±0x2000 waterfall below is real but all sit far above the ~418 the gain actually produces, so they were never the LKAS binder (they bound the merged/driver-assist signal). The absolute-addressed table findings (`0xE4180`=15360, `0xC9A88` per-gear, pointer arrays @`0xCB844` etc.) are UNAFFECTED. 2× lever: gain `0xC646C` 891→1782 + clamps `0xC61B2`/`0xC61B4` 512→1024. See [[reference-accord-lkas-window-ceiling]] / [[project-accord-torque-mod-v0]].

The 2020 Accord EPS arbitration stage `m_steer_torque_arbitration` (`FUN_00028ea6`, code.bin port 8193) is the first thing the LKAS setpoint feeds into after `s_lkas_process_steer_cmd`. Builds on [[reference-accord-lkas-torque-path]] and [[reference-accord-demand-aggregator-pipeline]] (this is the stage feeding the distributor); uses gp=0xFEDF8000 from [[reference-accord-gp-base-fedf8000]]. Decoded 2026-05-25, instruction/byte-verified.

**The limit is a FAMILY of curves, not a single 1-D speed->torque list.** Arbitration reads the setpoint s16 @ `gp-0x69ae` (`0xFEDF1652`) and **symmetrically clamps it to `±table_out`** (decompile lines ~120-150: breakpoint compare → LERP → magnitude clamp). The limit comes from **8 mode/gear-indexed pointer arrays**, index = byte @ `gp-0x674e`:

| label (renamed this session) | flash | role |
|---|---|---|
| `g_pArbSetpointLimitCurves` | 0xCB844 | the curve applied directly to the setpoint magnitude |
| `g_pArbCurveB_axisLo` / `g_pArbCurveB_axisHi` | 0xCBA74 / 0xCB924 | hi/lo pair blended by `bVar1 = (axis < 0x7d01=32000)` |
| `g_pArbCurve_c9a88/_cb7d4/_cbb54/_cbc34/_cbae4` | 0xC9A88… | further LERP curves (gain/limit; exact roles medium-confidence) |

Each array entry points to a LERP table at **`0xE4xxx`** with layout `{+2 bp[0], +4.. breakpoints, +0x12 bp_max, +0x14.. values, +0x24 val_max}`. **`cb844[0]` @ `0xE4180`** decoded = 9 breakpoints `[3200,3413,3627,3840,4736,5632,6528,7424,8320]` on interp axis `uVar20 = u16@gp-0x6a5e` (`0xFEDF15A2`), value row **CONSTANT 15360 (0x3c00)**. `cba74[0]`@`0xE4468` is a different 4-pt shape `bp[70,72,78,80]→[254,234,12,0]`. So "speed-in / max-torque-out" is a **slice** of a mode-selected, axis-blended family. Final gated cmd: **single writer** `st.h r16,-0x6b3c[gp]` @ `0x2a2ea` → `0xFEDF14C4` (`m_arb_final_torque_cmd`).

**BOTTLENECK CHAIN for a full-scale LKAS input x=4096** (the "first bottleneck in increasing the value" question): `s_lkas_process_steer_cmd` does `setpoint = clamp(x*-4, ±0x4000)` → at x=4096 that is `-16384 = -0x4000` **exactly on the rail** (first hard wall; ±0x4000 is a code literal). Then the descending staircase of caps: **arb limit ~15360** (first DATA-driven cut, a table read) → **distributor +4 lane ±0x2800 = 10240** (`FUN_00025c32`) → **mixer torque clamp ±0x2800** (`FUN_00026c80`, also ±0x4e20/±0x6400/±0xe10) → **shaper ±0x2000 = 8192** (`FUN_00042af8`, the tightest / binding final wall). So to raise delivered LKAS torque you must lift these in order; the ×−4 clamp and the arbitration table are the two earliest, and the shaper ±0x2000 is the narrowest.

**CORRECTION to TORQUE_PATH_AND_TABLE.md §3a / old `torque_transform_x4096.png` panel C:** the `0xC6518/0xC6534` row (speed `[0,10,25,50,80,120,200]` → limit `[12000,10000,10000,7000,7000,7000,7000]`) is **NOT read by the arbitration code** — it's a separate (likely managed/illustrative) curve. The live setpoint limit is the `0xE4xxx` family above. §3a's "LIKELY live speed-limit" role for `0xC6534` should be **downgraded**.

**Per-gear split (which curve actually varies by mode/gear) — verified 2026-05-25.** The family is mode/gear-indexed *in structure*, but whether the *data* varies per gear depends on the table:
- **`cb844` (the hard setpoint magnitude limit) is mode/gear-INVARIANT.** All 12 gear slots @ 0xE4180+mode*0x28 are byte-identical (const 15360); entries 6-11 are a 0x1000 block-mirror of 0-5. So "plot C" split by gear gives 3 coincident slices for this curve.
- **`c9a88` (0xC9A88, a torque shaping curve indexed by a 0..255 byte) DOES vary by gear.** Same breakpoint axis [0,12,20,24,32,64,96,128,160,240], different value rows: gear0 [0,16,28,34,48,92,124,148,162,172], gear1 [0,24,42,50,62,100,126,154,166,172], gear2 [0,11,26,35,56,129,158,172,174,180]. This is where the real "set of functions" lives.

So the answer to "is this a single list or a set of functions / max slice" is: a set of functions per gear; for the hard clamp the calibration fills every gear identically, for the shaping curve it does not.
