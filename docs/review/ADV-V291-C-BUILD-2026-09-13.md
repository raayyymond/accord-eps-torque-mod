## C1 — INDEPENDENT REBUILD — **PASS** [EVIDENCE]

**Method.** A rebuild script written from the pre-registration's cell table alone, deliberately *not*
importing `build_v291_tva.py` and not reading its constants. Start from the V282 image bytes; write the
three cal halfwords little-endian; assert-then-write the b3 rung displacement; **discover the CRC block
structure by walking the linked list in the image itself** (not from the builder's claim); recompute
every block CRC; hash.

**Block structure, derived from the image, not asserted:**

```
bootloader walk (with the verified 0xC6000 bridge) : 49 blocks
full linked-list chain (no bridge)                 : 50 blocks
0xC63E8 / 0xC63EA / 0xC6446  -> block [0xC6000,0xC6FFC)  trailer 0xC6FFC
0xC4BAA                      -> block [0x13000,0xC4FFC)  trailer 0xC4FFC
```

This **confirms the builder's claim independently**: 0xC4FFC does cover `[0x13000,0xC4FFC)` and the cave
byte therefore re-CRCs that whole block. Exactly two trailers move.

| trailer | V282 | V291 | zlib.crc32 | independent bit-serial CRC32 |
|---|---|---|---|---|
| 0xC6FFC | `0x75EADF72` | `0xED9B12BB` | `0xED9B12BB` | `0xED9B12BB` ✔ |
| 0xC4FFC | `0x4EB06B44` | `0x34CEC426` | `0x34CEC426` | `0x34CEC426` ✔ |

The independent CRC is a from-scratch bit-serial reflected implementation (poly `0xEDB88320`,
init/xorout `0xFFFFFFFF`), sharing no code with `zlib` or with the kit routine.

**Result:** independent rebuild sha256 = `a66f9c54…4657` = **the reported image exactly**.

**Second half — the script's own dry run.** `ACCORD_V291_DOSE=C10`, `ACCORD_V291_WRITE` unset,
`ACCORD_V291_TELEMETRY_BIT` unset (defaults to `b3`):


## DEFECTS (none blocking)

**D1 — [MAJOR, non-blocking] The assertion census is inflated ~5.6×.** 377 claimed substantive; 67
honest. 245 of section [5]'s 246 are entailed by [5]'s own first assertion; 42 of [9]'s are entailed by
[8]; 19 base-only decodes in [2]/[2b]/[2c] are marked substantive although the script's own definition
of "vacuous" is "entailed by the base sha256"; [12]'s 3 are entailed by `FROZEN` + the base hash.
**Recommendation:** count entailment, not call sites. The honest headline is *"67 substantive, of which
the load-bearing ones are [6] CRC, [7] the computed diff, [8] the non-circular cipher validation, and
[11] the built-image reader census with positive controls."* That is still a strong number and it is
defensible.

**D2 — [MODERATE] The output filename is a hard-coded literal, decoupled from the integers it names.**
`DOSES["C10"]["tag"]` is the string `"FBPOLE.10HZ.962.958-R24.4725"`; nothing asserts it matches `a`,
`b`, `r24`. **Demonstrated empirically:** a copy of the script with `r24=4722` and the tag left alone
passes **487/487 assertions**, reports the **identical census 377/60/50**, and emits
`…-R24.4725-…` as its filename with image sha256 `73bb2026…` — a different build under the reported
name. The silent bands:

| cell | values that pass every assertion while the name is unchanged | span |
|---|---|---|
| `a` 0xC63E8 | `{962}` only — the 0.05 Hz corner gate pins it exactly | 0 |
| `b` 0xC63EA | `{956, 957, 958, 959}` — the 0.2 % DC band | ±0.3 % |
| `r24` 0xC6446 | `{4722, 4723, 4724, 4725}` — the 0.1 % `k_gate` band | 0.057 % of the arm |

**Severity judgement: this is a labelling defect, not a safety one.** The worst silent mislabel is
−9.954 % where the name says −9.897 %. Physically negligible; it cannot admit a materially different
build under the V291 name. **Recommendation:** derive the tag from the integers
(`f"FBPOLE.{corner:.0f}HZ.{a}.{b}-R24.{r24}"`) so a transcription error renames the file instead of
mislabeling it.

**D3 — [MODERATE] No write guard; the "exactly ONE V291 rwd" check runs *after* the write.**

```python
out_img.write_bytes(bytes(code))        # unconditional — truncates any existing file
out_rwd.write_bytes(rwd)                # unconditional
... re-hash both ...
others = [n for n in v291 if n != out_rwd.name and not n.startswith("SUPERSEDED")]
check(not others, "exactly ONE flashable V291 rwd on disk")   # <-- fires only AFTER both writes
```

There is **no `exists()` / `'xb'` / `FileExistsError` guard anywhere in the script**. Consequences:
re-running at the same dose **silently overwrites the reported artifact**; running at a *different* dose
writes a second flashable V291 rwd and only *then* raises, leaving both on disk for the operator to
clean up. Given the kit's standing rule "exactly ONE flashable `.rwd` per build number on disk", the
check is in the wrong place. **Recommendation:** glob and refuse *before* writing; write with `'xb'`.

**D4 — [MINOR] `[10]`'s "independent rebuild … no shared state" is mislabeled.**
`independent_rebuild()` shares **every** module constant with `build()` — `FB_A_CELL`, `FB_A_NEW`,
`FB_B_*`, `R24_*`, `B7_INSN`, `B7_HW2_NEW`, `TELEMETRY`. The only thing that differs is how the CRC
blocks are located (`FF.crc_block_map` vs `V53.owning_block`). A wrong dose integer is reproduced
identically by both, so it cannot catch one. It is a **CRC-location cross-check**, which is worth
having — just not what the assertion text claims. *My* C1 rebuild is genuinely independent and matches,
so the substance is sound; only the label over-reaches.

**D5 — [MINOR] The docstring omits C10 — the dose actually built — from two of its own tables.**
§3's dead-zone/stick-floor table and §2(c)'s int32-headroom line list V282, C12 and C8 only. The missing
C10 row, read from the C10 run:

```
dead zone   |x| < 1.069 raw counts = 0.1336 deg/s   (x1.63 wider than V282's 0.656 / 0.0821)
stick floor |s| < 16.52                             (resting fb offset -20 -> -34 E-counts)
int32 headroom  s_ss = 185 419, a*s = 1.784e8 vs 2^31  ->  x12.04
```

All three are between the C12 and C8 values the docstring does give, so nothing is out of family — but
§2(c) states "the C8 margin is the smaller of the two", and with C10 present the ordering is
C12 ×12.20 > C10 ×12.04 > C8 ×11.90. No safety consequence; the docstring is simply incomplete about
the build that was cut.

**D6 — [MINOR] §1's "the r24 integers round DOWN" is off by one for C12.**
`floor(0.9390 × 5244) = 4924`, and the script uses `4923`. C10 (`4725 = floor(4725.893)`) and C8
(`4512 = floor(4512.462)`) are correct. The C12 error is in the **safe** direction (a deeper cut, further
below the gate) and C12 was not built. No action needed beyond the record.

## What a FAIL would have looked like, and why this is not one

Written before the work, per the pre-registration: a FAIL on C is an independent rebuild that does *not*
reproduce the hash; a diff carrying any byte outside the three cells, the rung and the two CRC trailers;
an rwd that does not decode back to the image; any wrong page CRC; a load-bearing claim about the edit's
effect that turns out to be a readback or entailed by the base hash; or more than one flashable V291 rwd
on disk. **None occurred.** Every one of C1, C2, C3 and C5 was checked by two independent
implementations, and C4's pre-registered criterion survived a claim-by-claim re-derivation.

The six defects are real and should be fixed, but they are properties of the *script's self-description
and its write hygiene*, not of the bytes in the image. The image is correct.

**Surface C verdict: PASS.**

*Findings arriving after the orchestrator accepts this verdict are reports, not licence to act.*
