## C1 — INDEPENDENT REBUILD — **PASS** [EVIDENCE]

**Method.** A rebuild script written from the **design memo's §4.4 cell table and §5 cave listing
only** — nothing imported from `build_v292_tva.py`, no constant read from it. Start from the V282
image; apply the four V291 edits; assert the hook site is the stock `mul` and the cave span is virgin
`0xFF`; write the 4 hook bytes and the 52 cave bytes; **discover the CRC block structure by walking
the linked list in the image itself**; recompute every block CRC with `zlib` **and** with a
from-scratch bit-serial reflected CRC32 (poly `0xEDB88320`), asserting the two agree on every block;
hash. The memo's §5 listing was first checked for contiguity and length: 15 rows, addresses chain
`0xC4C00 → 0xC4C34`, **52 bytes**.

**Block structure, derived from the image, not asserted:**

```
full linked-list chain (no bridge) : 50 blocks
bootloader walk (0xC6000 bridge)   : 49 blocks
0x28F8E / 0xC4BAA / 0xC4C00..33 -> block [0x13000,0xC4FFC)  trailer 0xC4FFC
0xC63E8 / 0xC63EA / 0xC6446     -> block [0xC6000,0xC6FFC)  trailer 0xC6FFC
```

Exactly two trailers move. This confirms the builder's claim independently.

| trailer | V282 | V292 | zlib.crc32 | independent bit-serial CRC32 |
|---|---|---|---|---|
| `0xC4FFC` | `0x4EB06B44` | `0x2C434E58` | `0x2C434E58` | `0x2C434E58` ✔ |
| `0xC6FFC` | `0x75EADF72` | `0xED9B12BB` | `0xED9B12BB` | `0xED9B12BB` ✔ |

`0xC6FFC` comes out **identical to V291's own recorded cal-block CRC** — the memo §4.3 number,
written before the build script existed.

**Result: independent rebuild sha256 = `d1128232…3aef33` = the reported image exactly.**

**Second route — the script's own dry run.** `ACCORD_V292_WRITE` unset, `ACCORD_V292_SCRATCH` unset,
no flags:

```
image SHA256 d1128232993d3a1dcfa4afecb279976f014e6c940f36d88b87db9f2aee3aef33
.rwd  SHA256 6d2784b5e27e2f21a909f552ac786f74fe28991dcbc275bf7ae03fb61f9fc20c
274/274 assertions passed -- census: 140 SUBSTANTIVE, 125 vacuous, 9 tautological
```

**Third route — a real write into a sandbox firmware root** (C5 below) produced artifacts whose
sha256 match the reported pair exactly.

(`git ls-files --error-unmatch` fails), so there is no history proving the on-disk script produced the
on-disk artifact. Three-route reproduction is the strongest available evidence and is sufficient.

Diff over the **whole 1 MiB**, not just the rwd region.

```

  [0x0C63E8,0x0C63E8]   1 B  9b       -> c2                  CAL   fb pole a  923 -> 962
  [0x0C63EA,0x0C63EB]   2 B  1806     -> be03                CAL   fb pole b 1560 -> 958
```

- Bytes **outside** the expected set (hook, rung, cave, 3 cals, 2 CRC words): **0**.
- Differing bytes in **`[0, 0x13000)`**, the region the rwd does not carry: **0**.
- **69, not 71**: `0xC4C10` and `0xC4C20` are themselves `0xFF` — the imm16 of each `andi 0x3ff`

- Cave span `[0xC4C00,0xC4C34)` is all `0xFF` on **V282 and on V291** — verified on both images.

## DEFECTS (none blocking)

**D1 — `V291_IMG_SHA` is declared and never used; the script never compares against the V291 image.**
`V291_IMG_SHA = "a66f9c54…4657"` sits at line 425 with zero references. Consequently the claim *"V291's
dose, byte-identical"* is established for the **three cal cells** (by S044's cal-block CRC pin) but
**not for the b3 rung at `0xC4BAA`**, which lives in the code block whose CRC necessarily moved. The
rung's identity with V291's rests on the script's own constants alone. **The claim is true** — I
verified it independently in C2 (V291 → V292 differs in exactly 58 bytes, all hook/cave/`0xC4FFC`) —
but the script does not establish it. One assertion would close it, using a constant already present:
load the V291 image, assert its sha256 == `V291_IMG_SHA`, and assert
`diff(built, V291) ⊆ [hook] ∪ [cave] ∪ [0xC4FFC,0xC4FFF]`. **Report, not licence to act.**

**D2 — the V291 supersede path is at 256/259 characters, 3 characters of margin.** The guard is
correct and fires, but the next build in this naming family, or a firmware root one directory deeper,
will hit it. Worth shortening the supersede prefix or the tag before the next cut.

**D3 (labelling, in the instrument rather than the build) — "On V291 it reads 0.52–1.00" is a
SIMULATION, presented as a reading.** The design memo §6 introduces the number with "Measured:", and
the build script's close-out banner prints *"FREE POSITIVE CONTROL: 0x14A byte 4 bit 3 … must read
duty ~0.000 at rest. On V291 it reads 0.52-1.00."* **V291 was never flown** — it is
`SUPERSEDED-DO-NOT-FLASH-…` and was never driven — so 0.52–1.00 is a 400-phase sweep through the
mirror model under an assumed symmetric oscillation, not an observed duty. The **V292 side is
byte-deterministic** (S083 drives the VM: `s` reaches exactly 0 from `s₀ = −1` and from `s₀ = −500`).
Two consequences worth putting in front of the operator:

1. Mark the V291 baseline **BELIEF (model)**, not EVIDENCE, on the page and in the read.
2. **The instrument has no on-car baseline at all.** On V282 — the build currently in the car — the b3
   rung points at `gp−0x3680` and publishes something else entirely; no flown build has ever carried
   this rung pointed at the filter state. A duty of 0.000 at rest is therefore consistent with *"the
   cave is live"* **and** with *"the rung is dead"*. The read should be stated as a **within-drive
   contrast** — non-zero b3 duty while the wheel is moving **and** ≈ 0.000 at rest — which is immune to
   a dead rung and needs no cross-build comparison. That is the form the `firmware-iteration` probe
   design law asks for, and it costs nothing to state.

## What a FAIL would have looked like, and why this is not one

Written before the work, per the pre-registration: a C-surface FAIL is an independent rebuild that
does not reproduce the reported hashes; a differing byte that cannot be attributed to hook, rung,
cave, cal or CRC; an rwd that does not round-trip or a block CRC that fails under either
implementation; an effect claim resting on a tautology or the base hash; more than one flashable V292
on disk or a V291 still flashable; a tag not derived from the integers; or a missing write guard.
**None occurred.** Three independent construction routes agree bit-for-bit, the diff is 69 bytes and
every one is attributed, all 50 blocks verify under two CRC implementations, 17/17 mutations are
caught, the census inflation is ×1.21, and the write guard demonstrably refuses a second write.

**Verdict: PASS.**
