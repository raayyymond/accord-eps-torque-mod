### What the rebuild had to get right, from the image, to land on that hash

- Both banks hold **28 DISTINCT records** — no aliasing. 112 Kd cells, 140 Kp cells written.
- V282's Kp bank is **not** one value: `205 / 248 / 266 / 307`, across **four different X-knot sets**

## C3 — THE rwd: **PASS**

- Single x31 block `[0x13000, 0x100000)`; headers `# ? / ! & %` with `/ = [39990-TVA-A110,
  39990-TVA,A160]`, key `BF109E`.
- **The kit trap is real and I hit it deliberately.** `roundtrip`'s default regex
  `39990[-]?([A-Za-z0-9]{3})[-_]?([A-Za-z0-9]{4})` yields `39990-TVA-A160` (hyphen). Cracking with that
  string returns **(None, None)**. Cracking with the comma form `39990-TVA,A160` succeeds:
  cipher `((i ^ 0x10) ^ 0xbf) - 0x9e`, the same table as `FF.V9B`.

- **CRC, two independent methods.** Kit routine: `walk_all_blocks` 50/50 and bootloader `walk` 49/49.

**Why.** Every Kp/Kd cell is carried by exactly one assertion that can see it — the byte **count** at [9].
That count is computed as *how many bytes differ between the base value and the intended value*. An
off-by-one that keeps the same **differing-byte width** (`248→120` and `248→121` both differ in one byte;
`128→0` and `128→1` both differ in one byte) is invisible to it. The semantic checks cannot help:

- [10]'s rail and `T(240)` read `lerp(X, Y, 240)`, which returns **`Y[-1]` only** — an interior knot is
  never sampled.
- [10]'s D check is an **OR** (`d_by_bank or d_by_clamp`); with `KD_METHOD = both` a corrupted Kd bank is
  masked by the zero D clamp.
- [11]'s tag reads **`Y[0]` of the live record only** and the *set* of records that changed, not their
  values.
- [7]'s coverage check only asks whether a byte is in `attributed`, not what was written there.

**The script's own suite reports 13/13 caught because of what it chose to mutate**: every one of its
Kp/Kd mutations either restores the *base* value (caught by the count dropping) or moves *all five knots*
(caught by the rail index and the tag). It never tests the realistic transcription error — one wrong knot
at the wrong level.

**Bounded severity (EVIDENCE).** The worst such error on the live record is small: one knot at 121
instead of 120 changes the delivered torque by **+9 counts (+0.78 %) at demand index 112 and nowhere
else** (neighbouring knots are still 120, so the LERP bump is triangular). `T(240)` is unchanged at 2461,
which is why the rail check is blind. An error on the *outer* knot would move the rail and **would** be
caught; the blind spot is specifically **interior knots**. For non-live records the consequence is
labelling only, contingent on a selector that was measured 7.

**This gap is closed for V293 by C1**: my rebuild, which derives every knot independently, is
byte-identical. The shipped artifact is correct.

### 🛑 DEFECT C5-1 — the tag ignores the D-clamp integer

`make_tag(kp_flat, kp_scope, kd_scope, r24, fb, dclamp, kd_method)` **never uses its `dclamp`
argument**. The `DCLAMP0` token is a typed literal selected by `kd_method`:

```python
kdtag = {"both": f"BANK.{kd_scope.upper()}+DCLAMP0", ...}[kd_method]
```

Demonstrated: with `kd_method="both"`, `make_tag(..., dclamp=0, ...)`, `dclamp=1` and `dclamp=10240` all
return the **same** string ending `…+DCLAMP0-KP.FLAT.120.ALL-R24.2048-…`. Changing r24, Kp or fb **does**
change the tag, as C5 requires; the D clamp does not. That is why the `D clamp 0 → 1` mutation is caught
by one assertion instead of two.

**Not a mislabel on this artifact** — I verified independently that `0xC61B6` reads **0** in the shipped
image, so `DCLAMP0` is truthful here. It is a verification gap: the name would keep claiming `DCLAMP0`
if the cell were ever not 0. This is V291's defect D2 in a cell the fix did not cover.

### 🛑 DEFECT C6-1 — "87 % of the delivered peak" is a unit error of ×6.13

Docstring §2[B]: *"D = (137·128)>>3 = 2192 counts of torque from a SINGLE COMMAND STEP — **87 % of the
delivered peak**."*

2192 is a **SUM-domain** count. 2505 (and 2461) are **output-domain** counts, after the forward gain
`G = 5346` and `>>15`. In consistent units:

| quantity | value |
|---|---|
| D, SUM domain | 2192 |
| SUM clamp | 15360 → D is **14.3 %** of the SUM ceiling |
| D expressed as delivered T | `(2192·5346)>>15` = **357** |
| delivered peak T | 2461 (byte-exact) → D is **14.5 %** |
| the docstring's figure | 2192 / 2505 = **87.5 %** |
| overstatement | **×6.03**, i.e. the motor gain `32768/5346 = 6.13` |

**This is a recurrence.** The same missing ×6.13 was recorded against V292's r24 fold. The *direction* of
[B] survives — D is a real feedforward kick from a single command step, and the tracer's independent
measurement that V282's D clamp already rails on 0.7 % of ticks stands on its own — but the *magnitude*
that motivates Kd → 0 is six times smaller than the docstring says. **Fix the sentence, not the build.**

### 🛑 DEFECT C6-2 — "0xCB7D4 Kd bank, every Y knot 128 → 0" is false for 20 of 28 records

The image carries **128 on 8 records and 64 on 20**. The claim holds for the live record `0xE511C` only.
The parallel Kp line (`0xCB994 … 248 → KP_FLAT`) has the same shape, but the script **contradicts it
itself** at [4] and in §2c, so only the Kd line is unflagged.

## WHAT I COULD NOT FALSIFY

Stated plainly, so the pass is not read as broader than it is:

- The **zero-edit control** reproduces the V282 base bit for bit (`0ea98d06…`, 0 differing bytes), so no
  "edit" in the file writes outside its own dose.
- The **`[13]` internal rebuild is honestly self-labelled** — it shares the module's constants and says so,
  and it cross-checks only the CRC-block locator and the splice. Surface C's C1 is the check that does
  not share them.
- The **CAL-ONLY claim holds**: not one byte below `0xC0000` changes, so V293 is outside the kit's only
  bricking class (V24/V27/V48B were all code caves).
- **`D ≡ 0` on the built image by both cells independently** — the Kd LERP reads 0 at every demand index
  0–240 on all 28 slots, *and* the D clamp reads 0. The prereg's A1 "either cell alone" clause is met.
- **The 427 delivered-torque tap and the 0x14A cave are byte-identical to V282** (cave hash `e9596ad9`,
  hook `0x55C0E` intact), so the instrument for this build's own edit is on the wire and untouched.

**Scope limit.** Surface C is the build script and the bytes. It says nothing about whether opening the
loop is *safe to drive* (surfaces A, B, D) and nothing about the delivered surface being the *right*
surface. It found no reason not to flash; it is not a reason to flash.
