### 0.1 A correction to `TRACE-2026-09-13-fb-lag-filter-bytes.md` section 4

The trace annotates `0x29F18 sar 0x7,r2` as *"P = (Kp product) >> 7"*. **It is not.** `r2` at that point

clamped to ±`0xC61BC` = 15360. **EVIDENCE — `disassemble_bytes(0x29EC0,72)` and `(0x29F08,48)`,
GhidraMCP, dry run.** So the model's `C = Kp/256 + (Kd/8)(1 − z^-1)` is **correct**; the brief's `>>8` is
right and the trace's note is a mislabel. No consequence for the build.

### 3.1 The premise — LR73 proportional to `0xC6446` — RE-DERIVED FROM THE LANE'S OWN ARITHMETIC

**EVIDENCE.** `decompile_function(0x3AC18)` giving `FUN_0003aa2c`, plus `disassemble_bytes(0x3ABD0,130)`:

```c
pcVar10 = clamp(*(short*)(gp-0x4f62), -5120, +5120);        // the lane input (D4 x bar)
if (*(char*)(gp-0x671d) != 0)    gain = [0xC6442];          // 1024, the LATCH arm
else if (*(char*)(gp-0x683c)!=0) gain = [0xC6446];          // 5244 -> 4725   <-- V291 edits this
else if (!bVar1)                 gain = [0xC6440];
else                             gain = LERP(...);
v    = (pcVar10 * gain) >> 10;                              // Q10, ld.hu     @0x3AC18/0x3AC20
u    = (v > 3) ? v-3 : (v < -3) ? v+3 : 0;                  // +-3 deadband [0xC61F6], POST-GAIN
r24  = clamp(u * (char)(gp-0x6752 = -1), -8192, +8192);     // @0x3AC42
*(short*)(gp-0x6ada) = r24;   iVar19 += r24;                // into the base-assist aggregate,
                                                            // total then clamped +-10240
```

Three consequences, all EVIDENCE:

1. **The lane is exactly linear in the gain between the deadband and the clamp.** The extension's
   premise holds there.
2. **The ±3 deadband is applied AFTER the gain**, so the true scaling is
   `k_eff(v) = (k·v − 3)/(v − 3) < k`. The cut is therefore **deeper** than 0.901 at small amplitude —
   the *safe* direction for the gate. `k_eff` is within 2 % of `k` for `v` above about 20, i.e. for
   ripples above ~0.5 deg/s at 7.3 Hz. The 7.3 Hz gate is about the strong-turn ripple, far above that.
3. **The ±8192 clamp would give `k_eff = 1` (gate 1.1163) but needs `|input| > 1600` of 5120.** With
   `|D4·B|` at 7.3 Hz loaded about 0.904 per raw rate count, that is **|x| about 1770 raw counts, i.e.
   221 deg/s** at 7.3 Hz (±4.8 deg amplitude). **Not reachable in normal driving.** So saturation does
   not void the extension. **BELIEF** on the reachability judgement; EVIDENCE on the threshold
   arithmetic.

**NEW: a mechanical explanation for `bof`'s unresolved 2353-vs-5244.** A subtractive post-gain
deadband of 3 depresses a magnitude or duty statistic by `(v−3)/v`. `2353/5244 = 0.4487` implies
`v = 5.44`, a wholly plausible typical post-gain lane magnitude at creep. **If that is the cause,
`GAIN_EFFECTIVE` is an artifact of not modelling the deadband, and the FLOWN 5244 is the correct
INCREMENTAL gain for the plant fits** — because a static deadband is an offset, not a gain, for
incremental dynamics. **This is BELIEF, not EVIDENCE — but it is the reading under which B3 FAILS.**

### 5.2 THE FOURTH CLAUSE FAILS — steady-state authority is NOT x1.00 +/- 1 %

The **linear** closed-loop DC ratio is 0.99961 — that is the number the design's `dc = 1.000` column
reports, and it is correct *as a linear number*. The **byte-exact** chain, run 40 000 ticks and averaged
over the last 4 s, says otherwise:

| `sp` (counts) | fit 289 | fit 192 | fit 225 | |
|---|---|---|---|---|
| +330 | 1.00139 | 1.00205 | 0.99820 | PASS |
| +33 | 1.00760 | **1.02919** | 0.99372 | marginal |
| −33 | 0.97890 | 1.00289 | 0.98895 | marginal |
| **+3** | **1.80000** | **1.33936** | **1.41495** | **FAIL** |

**Mechanism, byte-exact.** The input term is `floor(b·x/1024)`; its LSB in `x` is `1024/b`, which goes
**0.6564 to 1.0689 raw counts (x1.628 coarser)**. At `x` = 2–3 counts (0.25–0.4 deg/s) C10 resolves one
LSB where V282 resolves three, so the feedback reads roughly half of nominal, the error is larger, and
the loop delivers more rate. The `sar` floor is also asymmetric (`s = −1` is absorbing at every
`a < 1024`), so the DC error differs in sign between positive and negative `sp`.

**Describing-function gain of the byte-exact filter divided by its own linear transfer, at 20.3 Hz:**

| amplitude `A` (raw counts) | V282 | C10 |
|---|---|---|
| 1 (0.125 deg/s) | 0.9734 | **0.0735** |
| 2 (0.25 deg/s) | 1.1109 | **0.7251** |
| 3 | 1.0314 | 0.8561 |
| 5 | 1.0242 | 0.9530 |
| 8 (1.0 deg/s) | 1.0209 | 0.9807 |
| **16 (the measured ring, Addendum A8)** | 0.9982 | **1.0065** |
| 24 and above | 1.000 | 1.000 |

**The pre-registered read survives this; a deeper one would not.** At the ring amplitude (16 counts)
and at half-peak (8 counts) C10's feedback is intact, so the **half-peak decay 545 to 183 ms** metric is
safe. **Below about 4 raw counts (0.5 deg/s) C10's rate loop is effectively OPEN** (describing-function
gain 0.07 to 0.86) where V282's is still closed. A 10 %-decay or full-envelope ring metric **would not**
deliver the predicted improvement in its tail, and must not be substituted for the half-peak read.

**B4 verdict: FAIL** on the steady-state clause as written. **Severity: this is not a safety hazard** —
the absolute difference at `sp = 3` is 0.23 to 0.41 deg/s — but 91 % of engaged time sits at small
demand (`accord-kp-kd-schedule-x-axis-is-demand-index-16-125736-per-lsb`), so it is the *operating*
regime, not a corner case, and the `dc = 1.000` claim is false there.
