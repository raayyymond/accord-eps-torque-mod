# Adversary A — V282 cave encoding and execution timing — 2026-09-03

**Agent:** adv282a (subagent of `team-lead`). **Mandate:** make V282 FAIL on cave encoding and
execution. Tool policy: GhidraMCP only (`mcp__ghidra__*`) + Python for byte-level work, per
CLAUDE.md and the `firmware-decompile` skill.

**What a FAIL looks like, stated before running the pass:** any of — (a) a displacement that does
not decode to the claimed gp offset, or is odd/misaligned; (b) a byte outside the claimed 10-byte
diff; (c) a broken CRC chain; (d) an rwd that decodes to something other than the plain image; (e) a
comparator/mask/branch encoding that silently changed; (f) a demonstrated new register or new
overflow/sign-extension hazard; (g) a live cross-task race that did not exist in the base cave.

## Verdict: **PASS**

No defect found in cave encoding, comparator logic, byte masks, branch encodings, register usage,
CRC chain, or rwd↔plain-image correspondence. One item is left genuinely **open** (RAM

## 2. Instruction decode — Ghidra's own disassembler, both sides

The cave region `[0xC4B00, 0xC4B90)` is **byte-identical** between the V281r3 base and the
already-open, already-analysed `_v280_...` Ghidra program (verified in Python first — a required
positive control before trusting Ghidra's decode of "the base"). `disassemble_bytes(dry_run=true)`
on that program decodes the base cave cleanly: four `ld.h dispXX[gp], r6` instructions, identical
`hw1 = 0x3724` (opcode + reg2=r6 + reg1=gp=r4) in all four, at `0xC4B34`, `0xC4B40`, `0xC4B62`,
`0xC4B6E`.

I then imported the V282 image fresh into Ghidra (`import_file`, no auto-analysis, so this is a
clean read of the raw bytes) and ran the same `disassemble_bytes(dry_run=true)` over the same
range. Ghidra decoded the edited instructions as:

```
0xC4B34: ld.h -0x6ada, gp, r6      (was -0x6b94)
0xC4B40: ld.h -0x6b38, gp, r6      (was -0x4f64)
0xC4B62: ld.h -0x6ada, gp, r6      (was -0x6ae2)   <- same tap as 0xC4B34, reused
0xC4B6E: ld.h -0x6b94, gp, r6      (was -0x6b26)   <- reuses the OLD 0xC4B34 target
```

This is Ghidra's own decoder, not a hand-rolled displacement calculation, and it matches the
brief's claim **exactly**. `hw1` is unchanged in all four (confirmed both by the diff in §1 finding
no byte at any `hw1` position, and by Ghidra decoding identical opcode/reg1/reg2 fields on both
sides) — so reg1=gp, reg2=r6 are unchanged, and the operation is `ld.h` (sign-extending) on both
sides, never accidentally `ld.hu`/`ld.w`.

**Alignment/parity check (the `ld.bu` odd-displacement trap from the `firmware-decompile` skill does
NOT apply to `ld.h`, which requires bit0=0):** all three new displacements — `-0x6ada`, `-0x6b38`,
`-0x6b94` — are even (low nibble A/8/4, bit0=0 in every case), and so are the two raw `hw2` values
before sign interpretation (`0x9526`, `0x94c8`, `0x946c`, all even). No odd/misaligned displacement
was introduced.

## 4. Comparator, sign/abs handling, and clamp ranges — EVIDENCE, not asserted

Traced independently via `decompile_function`/`disassemble_bytes` on `code.bin` (stock, fully
analysed, 2086 functions):

- **`gp-0x6ada`** is written by `FUN_0003aa2c` (`st.h r24, -0x6ada, gp` @`0x3ad5a`). Traced `r24`
  back through the function: it is `clamp(-1 * <term>, -0x2000, +0x2000)` — a **hard ±8192 clamp**,
  built from two literal `movea 0x2000,r0,r24` / `movea -0x2000,r0,r10` + `cmovle`/`bgt` pairs
  (`0x3ac3e-0x3ac58`).
- **`gp-0x6b94`** is also written by `FUN_0003aa2c` (three `st.h ..., -0x6b94, gp` sites,
  `0x3acfa/0x3ad12/0x3ad20`), clamped to **±0x2800 (±10240)** via literal `movea 0x2800,r0,r12` /
  `movea -0x2800,r0,r12` (`0x3acf6`, `0x3ad0e`).
- **`gp-0x6b38`** is written by `FUN_00028ea6` (`st.h r1, -0x6b38, gp` @`0x2a23c`), clamped
  symmetrically to a **calibration cell** `tp+0x71b4` (= `0xC61B4`), not a hard literal. Read that
  cal byte directly from all three images in Python: **stock = 512, V281r3 base = 3072, V282 =
  3072** — confirming the brief's "±3072" figure and confirming V282 makes **no cal change** at
  this cell (matches the build script's own "no cal change" claim, independently corroborated, not
  taken on trust).

**Consequence for the `subr r0,r6` / INT16_MIN concern the brief raised:** all three cells are
hard- or cal-clamped to magnitudes ≤10240, far below `0x8000` (32768). `ld.h` sign-extends into a
32-bit register before `subr r0,r6` runs, so even in the theoretical case the clamp were bypassed,
negating a 16-bit-sign-extended `-32768` in 32-bit arithmetic gives `+32768` (a valid, in-range
32-bit result) rather than wrapping — but that scenario cannot occur here because none of the three
operands can reach anywhere near that magnitude. **This attack vector is moot, and moot for a
specific, cited reason, not by assumption.**

**Comparator semantics, confirmed against the decoded operands:** each block computes
`r7 = abs(first load)`, `r6 = abs(second load)`, then `cmp r6,r7` (V850: result = `r7-r6`) and
`bge` (branch if `r7-r6 >= 0`, i.e. `|first| >= |second|`), setting the flag bit only on that
branch. For V282: block1/2 → `r7=|gp-0x6ada|`, `r6=|gp-0x6b38|` → bit6 (`0x40` via `andi 0xbf` then
`or`) = `|gp-0x6ada| >= |gp-0x6b38|`. block3/4 → `r7=|gp-0x6ada|` (reused), `r6=|gp-0x6b94|` → bit5
(`0x20` via `andi 0xdf` then `or`) = `|gp-0x6ada| >= |gp-0x6b94|`. **This matches the brief's stated
formulas exactly**, independently re-derived from Ghidra's own decode rather than assumed.

Byte masks (`andi 0xbf`, `andi 0xdf`) and the `st.b .../-0x1514,gp` writes are byte-identical
between base and V282 (proven by §1's exhaustive diff — no byte at those instruction addresses
changed). Same for every branch (`bge`) encoding in the cave.

## 6. Execution context / task timing — the one place I found something worth flagging

Traced who calls what, in `code.bin`:

- `FUN_00055a98` (body `0x55a98-0x55c41`, contains the hook `0x55C0E`) has **no direct callers**
  (`get_function_callers` returns none — a null I did NOT trust per the skill's positive-control
  rule). Raw LE byte scan finds its address exactly once, as **data** at `0xB72D4`, inside a flat,
  contiguous array of `0x00055xxx`-`0x00056xxx` function pointers (`0xB72AC`-`0xB72D4`) — i.e. a CAN
  TX-frame-builder dispatch table, not an RTOS task table.
- `FUN_0002214a` — the function that directly calls both `FUN_0003aa2c` (writer of `gp-0x6ada` and
  `gp-0x6b94`) and `FUN_00028ea6` (writer of `gp-0x6b38`) — likewise has no `get_function_callers`
  hit, and `get_xrefs_to` also returned nothing (**a second confirmed instance of the skill's "null
  from the wrong tool" trap**). Raw LE byte scan finds it once, as data at `0xBB928`, embedded in a
  record that looks structurally like an **RTOS task descriptor** (neighbouring fields include
  `0xFEDEC000`/`0xFEE00000`-range addresses resembling stack bases, small counts, and a byte
  `0x01` that reads as a priority field) — a **different table shape** from the flat CAN-builder
  array at `0xB72D4`.

**So:** the hook that runs the cave (`FUN_00055a98`) and the code path that writes the three
compared cells (`FUN_0002214a` → `FUN_0003aa2c`/`FUN_00028ea6`) sit in what look like two different
scheduling contexts. I could not fully resolve the RTOS scheduler to prove periods/priorities from
here — that would need either the scheduler's own init/dispatch function decompiled or a live trace,
neither of which I did. This is a genuine **open item**, not a resolved PASS.

**However, it does not change the verdict, for a specific reason:** `gp-0x6b94` was **already** one
of the base cave's two read targets (it was `bit6`'s first operand pre-V282, now it is `bit5`'s
second operand post-V282), and it is written by the same `FUN_0003aa2c`/`FUN_0002214a` path. So
whatever cross-task relationship exists between the CAN-builder table and this write path was
**already present and already flown V105→V281** without incident. V282 adds one new cell to that
same relationship (`gp-0x6ada`, same writer function `FUN_0003aa2c`, hence same task) and one more
(`gp-0x6b38`, written by `FUN_00028ea6`, called from the *same* `FUN_0002214a` as `FUN_0003aa2c`) —
i.e. **V282 does not introduce a new task-crossing pattern, it reuses the existing one with two new
addresses**, one of which (`FUN_0003aa2c`'s output) is provably the same-task relationship as
before. No read-tear risk regardless, since the loads are `ld.h` on halfword-aligned, even
displacements — halfword accesses are atomic on this core, as the brief itself already noted.

**Unresolved, flagged explicitly:** whether `gp-0x6ada`/`gp-0x6b38`/`gp-0x6b94` are guaranteed
written (vs. holding cold-boot RAM state) before the very first `0x14A` transmission after power-on.
I did not trace the boot/BSS-init sequence to prove this. BELIEF (not evidence): V850E2 embedded
runtimes standardly zero-clear `.bss` before the scheduler starts, which would make a pre-first-write
read of these cells a defined `0` rather than garbage — but I have not confirmed this specific
startup code path. This is unchanged risk from the base cave (which had the identical property for
`gp-0x6b94` and `gp-0x6b26`), so it is not a new V282 hazard, but it is not closed either.

   `gp` address computation. All four displacements even, all three new targets land in the RAM
   region the base cave already used.
2. **Comparator rungs, clamp ranges, `subr` at -32768, branch/mask encodings** — PASS. All three

   not proven closed. Boot-time RAM initialisation of the three cells is likewise unproven (BELIEF

4. **Stack/registers** — PASS. Only r6/r7 used, unchanged, proven by the full-region diff finding no
   byte change outside the four `ld.h` hw2 fields and the CRC trailer.
5. **Full-file diff / CRC / rwd** — PASS. All independently reproduced: hashes match, CRC chain
   replays clean (0/50 mismatches), rwd decodes byte-identical to the plain image under the
   documented cipher.

**No defect found. Recommend PASS**, with the execution-context/boot-init item carried forward as an
