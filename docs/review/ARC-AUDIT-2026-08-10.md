## §4 — THE CODE-CAVE HISTORY

**Every success since V29 has been cal-only or a single in-place branch/displacement edit. Code
caves are this kit's ONLY bricking class — V24, V27, V48B all bricked the ECU.**

### The two mandatory gates

- **GATE 1 — RAM OWNERSHIP.** Every byte of the full multi-byte footprint proven free, **including
  writers** and register-indirect / 6-byte-extended-displacement accesses. **Static clearance alone
  is not sufficient** — `gp-0x1500` passed both static methods used at the time and still failed
  on-car. A live probe is the only reliable test. Poison region: `gp-0x1401..0x1502` (a subset of the
  `0xb7260` I/O-mailbox array).
- **GATE 2 — CLOSED-LOOP STABILITY.** Magnitude AND phase, of **every loop the touched signal is
  in**, especially the always-on base-assist loop. Never a single-frequency magnitude check. **GATE 2
  COROLLARY (2026-08-07):** "does not clip" and "is not a relay" are different statements — a
  saturation test alone is structurally blind to a surface that flattens onto a knee 17 counts under
  its own rail (V80's exact failure). Score flatness (`max/min` over the operating range), the
  describing function `N(50)/N(500)`, and distance-to-rail in counts — not just the clip percentage.

### The three brick mechanisms

| build | cave | mechanism | why it bricked |
|---|---|---|---|
| **V24** | trampoline at `0xC4E00`, FP-twin caves | **magnitude/type mismatch** | envelope-doubling via `shl 0x9` + float twin doubled to 2.0× where the int corridor only went 1.0× — **float 2× vs int 1× → fault** |
| **V27** | trampoline at `0xC4E00` | **ASYMMETRY, not magnitude** | the float twin doubled **wholesale**; the int corridor was only widened **corridor-only** (partial) — the two halves of a lockstep pair diverged, tripping the monitor that exists specifically to catch code-path divergence |
| **V48B** | 1 kHz biquad notch cave in the always-on base-assist loop | **(a) RAM collision** — biquad state `gp-0x14FA` **aliased a live monitor status byte**; **(b) unmodelled dynamics** — an unmodelled lightly-damped resonator was inserted directly into the always-on loop | recovered by reflash (not a permanent brick) |

★ **V40 is not a cave but teaches the same lesson**: `0xC6206`/`0xC6208`→`0xFFFF` bricked from the
**magnitude** of a cal write, not its direction — the same class of failure (an unchecked extreme
value) that a cave-specific gate would also have caught.

### The caves that WORKED — one continuous lineage, `0xC4B34`, hook `0x55C0E`

Every successful cave since V39 lives at the **same base address**, grown and rewritten in place —
never moved, never a second trampoline:

| build | cave size | payload | GATE 1 / GATE 2 basis |

**Why this class is safe where V24/V27/V48B were not:** every one of these is a **read-only
telemetry tap** into an existing CAN transmit path — it writes to a probe bit-field that already
exists on the wire (`0x14A` byte4), never inserts new dynamics into a control loop, and the
hook/trampoline mechanics (`0x55C0E`) have been re-verified byte-identical across dozens of builds.
GATE 2 is **structurally vacuous** for a probe (nothing it computes feeds back into the plant); GATE
1 has been re-proven on every build via a live-probe check (the discipline V48B lacked).

**A 2-byte in-place displacement or branch-condition edit (V88, V89's own control-cell changes) is a
categorically lower-risk class than a trampoline+cave** — this file's own standing rule. `0xC40D2`
(V89's actual lever) is exactly this class: a single `tp`-relative halfword, 1 reader / 0 writers,
no new code path.

**Pattern for the orchestrator designing a new cave:** reuse `0xC4B34`/`0x55C0E` if the new work is
telemetry (extend within the proven 62–68 B extent, in-place edit preferred over growing it); if new
control dynamics are needed, that is the V48B risk class and requires GATE 1 (live-probe RAM check,
not just static) **and** GATE 2 (magnitude AND phase, scored against the GATE 2 COROLLARY's flatness/
describing-function/distance-to-rail triplet, not a bare clip check) before flight.

## §6 — WHY IS THE MODELLED FRICTION TERM ZERO ~50% OF THE TIME? (V89 flight follow-up, 2026-08-10)

**Task:** V89 flew (routes 75/76, fault-free, best exposure in the kit's history), but `gp-0x6ae2`
(FRICTION×1024, the modelled Coulomb-friction term K1 acts on) reads near-zero on ~50% of engaged
frames (probe `b5` duty 0.5361 on r75, 0.4949 on r76 — **`b5` tests `|gp-0x6ae2| ≥ 64`, NOT literal
`==0`**, see the correction under "Method" below). This bounds `0xC40D2`'s effective dose to half the
drive and could mean either (a) the friction model is legitimately silent half the time, or (b) the
whole disturbance observer is dropping out. Method: `mcp__ghidra__decompile_function` /
`disassemble_function` / `get_xrefs_to` / `search_instructions` against the stock `code.bin` (this
region is **untouched by every build V38→V89** per §1 — `0xC40D0`/`0xC40D2` cal values differ, the
surrounding code does not — so stock's control flow applies unchanged to V89). Raw Python LE16 byte
scan run as the mandatory second method for the writer count.

### Item 1 — `gp-0x6752`'s writers, exhaustively [EVIDENCE]

**5 store sites in the whole 1 MiB image — cross-checked two ways.** `search_instructions` with
`operand_pattern="6752"` returned 59 hits; a raw Python scan for the disp16 LE16 encoding (`AE 98`)
independently found 52 of them and correctly missed the other 4 (they use the 6-byte
extended-displacement encoding the `firmware-decompile` skill warns a disp16-only scan is blind to —
confirmed, not just theoretical, in this trace). The remaining 3 of the 59 are **false positives**:
branch targets (`0x00026752`, `0x0006752a`, `0x0006752e`) that merely contain the digit string
"6752" as a substring of an address, not real `gp-0x6752` accesses. Net: **56 real accesses, 5 of
them stores**, all 5 confirmed by decompile:

| site | function | what it writes |
|---|---|---|
| `0x490c0` | `FUN_000490ac` | unconditional: `gp-0x6752 := 1` (after a shadow-pair check against `gp-0x4c2d`; mismatch → `FUN_0006b9fa` fault-4 raiser, no value written) |
| `0x48e68` | `FUN_00048a40`, case `bVar3==0x54` of a ~30-way switch | `gp-0x6752 := 1` if a parsed data byte `== ','` (0x2C) |
| `0x48e88` | same case | `gp-0x6752 := 0xFF` (i.e. −1) if the same parsed byte `== -6` (0xFA) instead |
| (2 more, `FUN_000497e6`) | same shadow-pair idiom, same two literals (1 / 0xFF) | `get_xrefs_to` finds **no static caller** for this function — either dead or reached only indirectly |

**No store anywhere in the image ever writes literal 0 to `gp-0x6752`.** This directly refutes the
working hypothesis in the task brief ("a direction/sign-of-travel latch with a dead band around
centre") — there is no rate, torque, or angle read anywhere in any of the 5 writer sites or their
enclosing functions. `FUN_00048a40`'s switch dispatches on a record-selector byte over what reads as
a parsed **configuration/calibration-record stream** (bit-flag accumulation into `DAT_fedf4b80..83`
across ~30 field types) — case `0x54` is one field of that stream, and its payload's third byte
(`','` vs `0xFA`) decides the sign written to `gp-0x6752`. This is a **config selector, not a live
per-sample signal**.

**The primary writer's call chain points at boot, not a periodic tick [BELIEF, well-supported].**
`FUN_000490ac` has exactly one caller, `FUN_00057e5e`, which in the *same* breath resets
`gp-0x67fa` — the assist-chain state gate (`accord-gp67fa-state-gate-on-assist-chain`,
`accord-check-gp67fa-reachable-set`) — to **1**, via the identical shadow-pair pattern
(`if gp-0x67fa==shadow: write 1,1; else fault`). `gp-0x67fa`'s live *reachable* state during driving
is `{11}` alone (memory, V64-measured) — `1` is not a driving state, it is an entry/reset value.
`FUN_00057e5e`'s only caller, `FUN_000843f4`, is referenced from a **data table at `0xbba74`** — read
directly (`mcp__ghidra__read_memory`): a table of 32-bit function-pointer entries, mostly a repeated
default handler `FUN_00084656`, with `FUN_000843f4` sitting at index 1 alongside a handful of other
distinct entries (`0x8412c`, `0x837c0`, `0x845fe`). This has the shape of a **state-dispatch table**,
and slot 1 lining up with `gp-0x67fa`'s own state-1 entry value is unlikely to be coincidence. The
natural reading: this is the **state-1 (entry) handler of the assist-chain state machine itself** —
run once when the chain (re-)enters state 1, which happens at power-on before the chain progresses
toward the live state 11, not on a steady 1 kHz/100 Hz tick. **I did not trace the dispatcher's own
scheduling to full certainty** — this is BELIEF, not proof — but it is consistent on every axis
checked (the literal values written, the co-located state-gate reset, the table shape).

**⇒ `gp-0x6752` should sit at a fixed ±1 for essentially the entire drive, set once near boot.** A
sustained polarity=0 explanation for V89's ~50% duty does not hold up against this trace.

### Item 2 — polarity-zero vs gate-failure-stale-zero [EVIDENCE, structural]

Confirmed directly from `FUN_0003b8f6`'s decompile (already quoted in the task brief, re-verified
here): `gp-0x6ae0` and `gp-0x6ae2` are written **only** on the enable-gate's success path — the very
last two statements before the shared exit (`goto LAB_0003bc16`). The gate-fail path writes **only**
`gp-0x6bf6:=0x7FFF`, `gp-0x6bfc:=0x7FFF`, `gp-0x6c00:=0xFFFF` — it never touches `gp-0x6ae0`/`gp-0x6ae2`.
**So yes, a near-zero reading in `gp-0x6ae2` could be stale**, held over from the last successful
call, and a gate failure and a live near-zero computation are indistinguishable from `gp-0x6ae2`
alone. This is exactly the concern in the task brief, confirmed structurally rather than assumed.

### A third explanation, better supported than either of the above [BELIEF, physically grounded]

Given item 1 (polarity ≈ fixed ±1, not oscillating), the near-zero duty is much more economically
explained by the **arithmetic of the Coulomb term itself**, with no need to invoke either polarity=0
or gate failure:

```
ratio       = clamp(polarity * motor_rate(gp-0x6abc) * 12 / cal(0xC40BC), ±1.0)   # cal = 600 on V89
FRICTION    = EMA(ratio * |model| * K1/1024 + 0 * ratio, a = cal(0xC40D0)/4096)   # a ≈ 0.0996, K0=0
gp-0x6ae2   = FRICTION * 1024
```

With `polarity` pinned at ±1, `ratio` is a clamped LINEAR function of `motor_rate` that **saturates
to ±1 once `|motor_rate| > 50 counts`** (`600/12`) and is exactly proportional to `motor_rate` inside
that ±50-count band, including passing through **exactly 0** every time `motor_rate` crosses zero.
`motor_rate` reversing sign is not rare — it is the same signal underlying the ~7–9 Hz micro-ratchet
band this whole kit has been characterising (`accord-ratchet-is-a-lightly-damped-resonance`,
`accord-ratchet-axis-is-wheel-rate`). `FRICTION` is a **fast** EMA of `ratio × |model|`
(`a ≈ 0.0996` at 1 kHz ⇒ time constant ≈ 10 ms), so every rate reversal drives `FRICTION` toward zero
within a handful of milliseconds, and the probe's actual threshold (`|gp-0x6ae2| ≥ 64`, i.e.
`|FRICTION| ≥ 0.0625` out of a ±10.0 range) is a **small** fraction of full scale — easily crossed on
every reversal. **A ~50% duty of "below the probe's threshold" is the expected signature of a
sign(rate)-driven relay term run through a fast EMA on ordinary steering input with frequent rate
reversals — not evidence the observer is dropping out.**

**This is BELIEF, not measured** — it requires `motor_rate`'s (`gp-0x6abc`) actual zero-crossing rate
on-car, which is not in hand this session. But it is the only one of the three candidate explanations
consistent with the writer trace in item 1, and it does not require assuming either a broken gate or
an oscillating polarity signal for which no writer exists.
