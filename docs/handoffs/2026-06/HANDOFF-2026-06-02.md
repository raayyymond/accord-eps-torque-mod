## The corrected causal model (this is the load-bearing part)

The "2× output" behavioral package = **V18**: gain `tp+0x746c` 891→1782 (~1.74×) + output clamps
`tp+0x71b2/0x71b4` 512→1024. **The gain is LKAS-command-scoped only** (operator-confirmed) — it does
NOT scale driver-assist (manual) torque.

Build history and what each fault actually was:

| Build | Added vs V18 | Behavior |
|---|---|---|
| **V18** | (baseline 2× package) | Drove. Had an **LKAS-time** accumulation EME *while driving*. **Did NOT fault on an in-place manual turn.** |
| **V21–V23** | integer envelope ×2 (`shl 0x9`), partial FP edits | **Died at STARTUP**, every time. Never reached the steering path. |
| **V24** | envelope ×2 + FP-twin ×2 + widened/neutralized consistency checks | **Boots clean.** Faults on a **manual in-place ~20° turn** (hard EPS off). |

Two **distinct** faults that we previously conflated:
1. **V18 fault** — appears *while driving with LKAS* (2× LKAS command vs the stock envelope). This is
   what originally motivated doubling the envelope.
2. **V24 fault** — appears on a *manual in-place turn* (driver-assist torque through the now-doubled
   SHARED envelope). **This one we created.**

**Why V24 faults on a manual turn (deduced by elimination):** the only *behavioral* delta between V18
(fine on a manual turn) and V24 (faults) is the **envelope-doubling** (`shl 0x9` + the FP-twin caves).
Everything else V24 added (widening bits 1/2, neutralizing inline check A) is *permissive* — it can only
prevent a fault, never cause one. The envelope `shl` lives inside **`s_motor_torque_rate_shaper`
(FUN_00042af8)**, which shapes the **final motor torque = driver-assist + LKAS**. So doubling the
envelope let the *driver-assist* torque ramp/shape differently during a hand turn → tripped a monitor
that stock/V18 never hit. **Our envelope edit was global, not LKAS-scoped — unlike the gain.**

## The open problem / decision for next session

The envelope is **shared** between driver-assist and LKAS. Doubling it globally (to help fault #1) broke
driver-assist (fault #2). The path forward hinges on two verifications and one design decision:

- **VERIFY-A:** Confirm the `shl`/envelope (`gp-0x3574`/`gp-0x3578`) path feeds the **driver-assist**
  motor torque and not only an LKAS branch. (Operator believes the rate-shaper is shared.)
- **VERIFY-B:** Identify **which specific monitor** the doubled driver-assist torque trips on a turn.
  Candidates: rate/command-consistency bits **4 (slew), 32 (torque-step), 64 (rate, tightest thr
  1.5e-4)** in FUN_00043e44; OR envelope bits **1/2** firing on a larger *dynamic* discrepancy than the
  static-startup case we widened for (±15/1024 may be enough at rest but not mid-turn).
- **DECIDE:** Either (i) **scope the envelope boost to the LKAS contribution only** (leave driver-assist
  on the stock envelope), or (ii) determine whether the 2× LKAS gain even needs an envelope change once
  properly scoped — possibly the whole global-envelope thread was mis-scoped.

**Foundational question still unresolved (flagged repeatedly, never closed):** is the envelope
(`gp-0x6af6`/`gp-0x3574`) actually used to **clamp the command**, and is it the limit the V18 LKAS-time
accumulation EME checks against? Answer this before doing more envelope work.

## Verified firmware facts (cold-disassembled this session; trust these)

Register base: **gp = 0xFEDF8000**, **tp = 0xBF000**. "gp-0xNNNN" = 0xFEDF8000−NNNN; "tp+0xNNNN" = 0xBF000+NNNN.

**FUN_00042af8 — integer torque rate-shaper (`s_motor_torque_rate_shaper`):**
- Envelope IIR states: `gp-0x3574` (upper, 0xFEDF4A8C), `gp-0x3578` (lower, 0xFEDF4A88).
- LERP3 output scaled `shl 0x8` (stock) → IIR. Sites: `0x42DAE`/`0x42DCA` (upper), `0x42F16` (lower).
  V24 patches these to `shl 0x9` (envelope ×2).
- De-scale `sar 0x8`: `0x43136` (upper), `0x43142` (lower) → integer shadows `gp-0x6af6` (upper,
  0xFEDF150A), `gp-0x6b00` (lower, 0xFEDF1500), stored ~end of function.
- **INLINE envelope consistency check (A) @0x43172–0x431c0:** `trunc(float[gp-0x6db0]*1024) −
  int16[gp-0x6af6]` within **±5** → else fault to **sp+0x30** (upper). Lower: vs `gp-0x6db8`/`gp-0x6b00`
  → fault code 2 to **sp+0x18**. Upper centering/width: `addi 0x5,r15`@0x4318e + `cmp 0xb,r15`@0x43196
  (`setfnc`); lower `addi 0x5`@0x431b2 + `cmp 0xb`@0x431b6 (`bc`). These faults feed FUN_00016de6(**0x1c**).
  **NOTE: cmp is UNSIGNED; cmp imm5 SIGN-EXTENDS → max real symmetric window is ±7. `cmp 0x1f` = `cmp -1`
  = "always in range" (neutralize).** V24 neutralizes (A) this way.

**FUN_00043e44 — FP monitor (the EME accumulator):**
- **FP envelope twins:** `gp-0x6db0` (upper, 0xFEDF1250) written `st.w lp,-0x6db0`@0x449f4;
  `gp-0x6db8` (lower, 0xFEDF1248) `st.w r20,-0x6db8`@0x44a30. **`lp`/`r20` = envelope × direction-sign
  (formed @0x4461e/0x44624 and @0x4462e), NOT the command** (a tracer mis-stated this — do not believe
  "lp = command"). `lp`/`r20` are live-unchanged from formation to store, so doubling them at the
  bit-1/2 checks (@0x4463a/0x44662) propagates to the twins. These twins are read ONLY by check (A).
- **Weighted error bits** summed @0x44926–0x4493a: bit1(0x4463a)/bit2(0x44662) = **ENVELOPE** checks
  (FP twin vs `gp-0x6af6`/`gp-0x6b00`); bit4(0x44784, slew vs `gp-0x6b0a`)/bit8(0x447a0, vs `gp-0x6b04`)/
  bit32(0x448a0–0x448ee, vs delivered `gp-0x6b98`)/bit64(0x4490e) = **COMMAND/RATE** domain.
- Thresholds: shared positive `0x3ba00000` = **5/1024** @0x4463e; per-bit negatives `0x4460`→0xbba00000
  @0x44646(bit1)/0x4466a(bit2)/0x4478c(bit4). **bit64 = `0x39200000` ≈ 1.5e-4 @0x4490e (32× tighter).**
- **EME decision:** accumulator `r7` vs **128.0** (`0x43000000`) `cmp`@0x44a2e → `bgt`@0x44a34 →
  `jarl 0x000462e6(0x3f1b)`@0x44a4c → FUN_00016de6(**0x1d**) → **DTC 0xF00049**. Dwell SM @0x4493e–0x449cc
  uses `gp-0x3550` (accumulator) / `gp-0x3540` (dwell byte). The V19/V20 "SM1/2/3 raises" acted on this
  accumulator/dwell threshold (band-aid; V20 hit the ceiling).
- Other RAM: delivered torque `gp-0x6b98` (0xFEDF1468, clamped ±0x2000); governor `gp-0x4f64`.

**Calibration (block #48 [0xC6000,0xC6FFC)):** gain `tp+0x746c`@0xC646C (891→1782); clamps
`tp+0x71b4`@0xC61B4 & `tp+0x71b2`@0xC61B2 (512→1024); RAMPSTEP `tp+0x74de`@0xC64DE (0x11→0x1B); IIR α
`tp+0x7418`@0xC6418 = 10.

**Cipher / CRC:** V9B canonical = keys (0xBF,0x10,0x9E), ops (xor,xor,sub). CRC blocks recomputed:
#48 @0xC6FFC (cal), main @0xC4FFC. Cave base for hooks = `0xC4E00`. Build self-check walks all 49
bootloader CRC blocks.

## Mistakes corrected this session — do NOT repeat

1. **The gain does NOT cause driving/turn faults.** It is LKAS-command-scoped; a manual in-place turn
   has no LKAS command. (I wrongly blamed the gain; operator corrected.)
2. **`lp`/`r20` are the ENVELOPE × direction, not the command.** A firmware tracer asserted "lp =
   command" and built a "26% gain-vs-envelope mismatch" theory on it — that theory is WRONG.
3. **The emulator agent twice fell back to static/idealized arithmetic** (assumed zero FP-vs-integer
   discrepancy → "diff=0, full margin"). It did NOT deliver a true dynamic V850 measurement. The actual
   runtime discrepancy is **unmeasured**. Treat its "passes with full margin" as unproven.
4. **V18 did NOT fault on a manual in-place turn** — so the turn-fault is V24-specific, i.e. caused by
   *our* envelope-doubling, not inherited from V18.

## Reusable insight (candidate memory)

Doubling a monitored quantity doubles its FP-vs-integer rounding discrepancy against **fixed-absolute-
tolerance** consistency checks, so pure path-alignment (Option 1) can't satisfy them — you must widen
or neutralize the check (Option 2). **But scope matters:** the torque envelope lives in a *shared*
rate-shaper, so a global envelope change hits driver-assist, not just LKAS. Propose adding this as a
`reference_*` memory after next session confirms the shared-path mechanism.
