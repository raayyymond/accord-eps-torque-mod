## What happened (V30 road test → this debug)

**V30 was FLASHED and drove well — far better than V18 and all prior builds.** No hard EME (DTC). Every turn
that used to trigger a soft EME stopped triggering one — **except one very hard, *sustained* turn that LKAS
held by itself**, which still soft-EME'd (recoverable, no DTC, operator took over). The operator's question:

## ROOT CAUSE (instruction-verified this session on stock `code.bin`)

The soft-EME integrator `gp-0x3570` (FUN_00042af8, update block `0x431c4–0x4327c`) winds up on
`(command − bound)`, and **the bound is NOT the corridor alone — it is the same THREE-WAY MAX/MIN wall**:

```
upper bound r29 (@0x4318a) = MAX( corridor[cal 0xC674E], IIR-envelope gp-0x3574>>8, boost[cal 0xC6760] )
lower bound r27 (@0x4316e) = MIN( corridor[cal 0xC675A], -IIR gp-0x3578>>8,          -boost )
```

V30's build comment assumed "command − corridor" — that was the modeling gap. **The corridor arm is GATED**
(`0x43110–0x43134`, verified by direct disasm): when the column position-error `|gp-0x6bf0| ≤ cal 0xC6156
(= 9216)`, **BOTH corridor arms are forced to 0** (sign-selective when |err|>9216: one side kept, the other
zeroed; also hard-zeroed if LKAS disengaged / sensor out-of-range / a speed gate). `|pos_err| ≤ 9216` is
exactly the regime of a hard turn LKAS is **holding well** (small tracking error).

With the corridor gated off, the bound collapses to `max(IIR, boost)`. On a **HELD** turn the wheel is not
rotating → **boost ≈ 0** (boost is keyed on steering ANGULAR RATE `gp-0x6ac2`) and **IIR small** (keyed on
column velocity ≈ 0). So the bound collapsed toward the small residual (~stock 512-ish), and the **2× LKAS
hold-command (~1024, COMP ≈ 0 hands-off)** sailed past it → integrator wound up → SM2/SM3 cut. At stock 1×
the ~512 command fits under that residual — which is why this is a **2×-only** event and why V30 fixed every
*other* turn (those had the wheel displaced from target → corridor *active* → its 4096 held). **V30 widened
the one arm that is switched off in precisely the regime that failed.**

Bonus resolutions from the operator's data: (1) IIR being small on a held turn **resolves the contested IIR
input identity → column velocity, not LKAS command** ([[reference-accord-lerp3-gp3574-chain]]). (2) Hands-off
rules out the driver-torque plausibility path ([[reference-accord-driver-override-plausibility-eme]]) — this
was the SM2/SM3 integrator, matching the road-logged signature ("sustained, opposing, column stationary").

SM arming (cal-verified): SM2 arms @ `|integrator|·1092/1024 ≥ 0xC6422 = 16384`; SM3 arms when the integrator
saturates at its clamp `0xC61DC = 30720`; either → `authority=0` → instant cut, ~10 s ramp recovery.
SM1 (`0xC61DE = 2048` arm) is velocity+opposition gated (instant anti-runaway) — separate, untouched.

⚠ **Precision (corrects an earlier "ungated" claim): boost is NOT unconditionally present — it is
AUTHORITY-gated.** A state machine (`gp-0x3562`, `0x42fb8–0x43016`) force-zeroes the boost value *after* the

returns to 0 (`r13 = gp-0x6966 = (|integrator gp-0x3570>>15| × 1092[cal 0xC61DA]) >> 10` — the same authority

fixpoint:** at the EME *initiation* instant — a hands-off held turn, authority ≈ 0 — boost is in its "on"
state and floored to 4096, so `bound ≥ 4096 > command (≤3584)` ⇒ the integrator can't wind up ⇒ authority
never climbs to the 16384 latch point ⇒ boost never zeroes. The runaway/both-off state (corridor off via its
authority-gate **and** boost latched off — the V30 EME *end*-state) is therefore **unreachable from normal
operation**. The corridor (V30) couldn't do this because it's *driver-assist*-gated (gone hands-off); boost is
*authority*-gated (present at authority≈0). Full per-arm gating proof + the verified `r13`=authority chain:
`memory/reference/firmware/reference_accord_soft_eme_bound_arm_gating.md`.

### Why lockstep-safe (avoids the V25–V27 hard-fault class) [V, floattwin trace + reads]

The boost arm exists **symmetrically** in BOTH walls: int wall `gp-0x6af6/b00` = `LERP(0xC6760, |rate gp-0x6ac2|)`
(FUN_00042af8); float twin `gp-0x6db0/db8` = a 3-way max/min that **includes** `LERP(0xC65B8, same rate)`
(FUN_00043e44, boost enters upper @`0x4440a`, lower negated @`0x445c8`). Float Y = int Y / 1024 **exactly**
(stock 0/1536/2048 ↔ 0.0/1.5/2.0). A matched edit moves both walls equally → monitor delta stays 0
(`|4.0×1024 − 4096| = 0` ≤ ±5 LSB), INCLUDING at rest (rate≈0 → both return Y[0], moved together). This is
the **opposite** of V26's `0xC6664` LERP_B mistake (a float-ONLY multiplier with no int counterpart → +2.0
rest offset → hard fault). Boost has an int counterpart, so it is safe.

## ⚠ SAFETY TRADE (operator chose this — name it plainly)

With the envelope floored at 4096 ≥ worst-case command 3584, the integrator never winds up in ANY regime
(held or active, with or without driver override) → **the SLOW-WINDUP soft-EME cutback (SM2/SM3) is
functionally inert**. That is the intent (hold 2× LKAS, no soft EME on hard sustained turns). It is the same
trade V30 *aimed* at but now actually effective in the held-turn regime. **The INSTANT anti-runaway SM1
(velocity + command-opposition, separate path) is UNTOUCHED and still fires on a genuine fast-opposition
runaway.** Hard-EME (DTC 0xF00049) lockstep fully intact. The proportional alternative (raise SM thresholds,
V19) only DELAYS the cut on a sustained exceedance (the integrator still saturates → SM3) — it does not
prevent it, which is why the floor was chosen.

**Residuals [I]:**
1. **4096 may be larger than needed.** It is the conservative worst-case (1024 + 2560 COMP). If the realized
   COMP is small, a smaller floor (e.g. 2048–2560) would still hold the LKAS-alone case with more retained
   SM2/SM3 sensitivity. Right-size via the `gp-0x6ac0` comp-range trace (V30 residual #1) if desired.
2. **Flattening boost removes its turn-rate-boost function**, but the flat floor (4096) exceeds anything boost
   ever provided (≤2048), so no authority is lost — the bound is just uniformly generous. At high column
   velocity the IIR arm (≤12288) dominates anyway and the floor is moot.
3. The speed-gate operand identities (`r13` variable vs `r21=cal 0xC641A=0` threshold @`0x43028`/`0x43112`)
   were noted but not fully walked — irrelevant to V31 (boost is ungated) but matters for the full gate map.
