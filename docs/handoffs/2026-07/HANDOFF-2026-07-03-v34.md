## 0. One-line state

**V32 and V33 did not fix the gentle EME because they attacked the wrong gate.** The engage-SM disengage
decider `FUN_00040d58` has, in its ENGAGED/HOLDING branches, a **SECOND** disengage that V32/V33 never
touched: the **`gp-0x6cc4` angle/position consensus gate** (vs cal `0xC6354` = 4825). A road bump spikes the
angle accumulator past the consensus band (no debounce) → the decider leaves the delivering state → LKAS drops
and re-arms = the gentle EME. **V34 = V33 + two surgical code NOPs** that make the decider ignore the
angle-consensus result and stay engaged. Cal `0xC6354` is deliberately NOT touched (it has 14 readers / 5
roles and drives a lockstep-shadowed pipeline — raising it risks a HARD fault). **BUILT, self-checked
(49/49 CRC), decider byte-identical to stock except the 4 NOP bytes, UNFLASHED study artifact.**

## 1. Why V33 did not fix it — the missed second gate [V — radare2 v850.gnu, verified this session]

V33 raised cal `0xC6312` (320→65535) to disable the sensor-A torque-**magnitude** disengage. It was built
correctly (byte-verified: the flashed image really has `0xC6312 = 0xFFFF`, only 6 bytes differ from V31) — the
EME still occurred because that gate was not (solely) the cause. Full decode of `FUN_00040d58`:

```
ENGAGED (param 2), 0x40dc6:
   gp-0x6a62 == 0xffff      -> return 2 (disengage)   [invalid-sensor sentinel; V33 KEPT this]
   gp-0x6a62 >= cal 0xC6312 -> return 2 (disengage)   [torque magnitude; V33 DISABLED this (65535)]
   0x40ddc jarl FUN_000406ae ; 0x40de2 be 0x40e1a     -> return 4  <== SECOND GATE, V33 never touched
   else                     -> return 0 (STAY / deliver)

HOLDING (param 3), 0x40dea:
   gp-0x6a62 == 0xffff / >= 0xC6312 -> return 2
   0x40e00 ld.w gp-0x6cc4 ; ABS ; 0x40e10 cmp cal 0xC6354(=4825) ; 0x40e12 bh 0x40e1a  -> return 4  <== SECOND GATE
   else                     -> return 0 (STAY)
```

`FUN_000406ae` (0x406ae) is a **4-history-array consensus monitor**: returns 0 ("not confirmed") when the
current `gp-0x6cc4` deviates from its recent consensus by **≥ cal 0xC6354 (4825)**, OR when history is
insufficient. `gp-0x6cc4` (= `0xFEDF133C`) is an **angle/position-domain tracking accumulator** — three
writers, all with mod-2048/4096 wrap-correction idioms (`sar 11 / shl 11 / sub`; angles wrap, torque does
not). Independent re-derivation this session: `gp-0x6cc4_new = gp-0x6cc4_old − gp-0x35fc`, an integrator.

**So a road bump on a curve mechanically jolts steering angle → `gp-0x6cc4` spikes past the 4825 consensus
band for one cycle (no debounce) → decider returns 4 → LKAS leaves the delivering state and re-arms = the
gentle EME.** This is the *direct* "bump triggers it" path, and it explains the whole torque-vs-angle
confusion: the CAN log showed torque leading, so the earlier hypothesis chased the torque gate — but the
firmware gate that fires is on the **angle/position** channel V32/V33 left alone.

### Why the prior session concluded "torque magnitude ONLY"
Its engage-SM memory documented ENGAGED/HOLDING as `gp-0x6a62 >= 0xC6312 ONLY`. Five compounding reasons it
missed the second gate: (1) it **stopped at the first gate** — the `gp-0x6a62` check comes first, matched the
torque hypothesis, and the branch body past `0x40dd6`/`0x40df8` was never walked to `0x40e1a`; (2) the whole
V33 session was aimed at a **microscopic detail** — which instruction reads `0xC6312` (`0x40db8/dd0/df4` vs
the gp-0x6a62 value reads) — never zooming out to "what else does this branch check"; (3) **disengage was
framed as return-2**; the angle gate returns `mov 4` — a different value that also leaves the delivering
state; (4) the angle gate is **opaque without decompiling `FUN_000406ae`** (a 460-byte consensus monitor) and
multi-hop-tracing `gp-0x6cc4`; (5) **confirmation bias** from the operator's own "torque leads velocity, it's
a torque trigger" read of the CAN log terminated the search once a torque gate was found (the exact
"no false summits" hazard).

## 2. What V34 changes — 2 code NOPs (in-place, size-preserving, no trampoline) [V — built + decoded]

```
0x40DE2:  be 0x40e1a  (c2 1d)  ->  nop (00 00)   ENGAGED: ignore FUN_000406ae()==0  -> fall through to STAY
0x40E12:  bh 0x40e1a  (cb 05)  ->  nop (00 00)   HOLDING: ignore |gp-0x6cc4|>4825    -> fall through to STAY
```

After each NOP the code falls through to the existing stay path (`ld.bu -0x35b6[gp],r12 ; br 0x40e68`,
r12=substate=0 = the canonical "deliver" return). The `jarl FUN_000406ae` **call is retained**, so its side
effect (conditional `st.w r12,-0x35ac[gp]` at 0x40862) still runs exactly as stock — only the decider's
**reaction** to the result is nulled. `mov 4,r12` at `0x40e1a` is now dead code (3 refs total in the function:
the 2 NOP'd branches + the label; nothing else reaches it).

**V34 also keeps V33's `0xC6312 = 65535`** (operator-directed belt-and-suspenders — kills the torque-magnitude
return-2 path too). Net: on V34 the ENGAGED/HOLDING decider cannot leave the delivering state on EITHER
`gp-0x6a62` magnitude OR `gp-0x6cc4` angle-consensus. The `gp-0x6a62 == 0xffff` invalid-sensor sentinel is
**still intact** (a genuine dead-torque-sensor fault path — and the retained lower-probability residual, see §4).

### Why NOT just raise cal `0xC6354` (the clean-looking cal lever) — REJECTED AS UNSAFE
Whole-image scan: `0xC6354` has **14 readers across 5 roles** — not only the two disengage gates, but also a
±window gate and a scale factor INSIDE the pipeline that computes `gp-0x6cc4` itself, plus a mode selector.
`gp-0x6cc4` is lockstep-shadowed (`gp-0x4D0C`, `FUN_0006b9fa` fault check). Raising `0xC6354` would perturb the
tracking pipeline and could **desync the shadow → a HARD EME (DTC)** — the V25–V27 fault class. The code-NOP
approach touches none of that.

## 3. Consequence sweep — upstream + downstream of the 2 NOPs [V, two independent tracers]

**Scope (exhaustive):** `FUN_00040d58` has exactly **7 whole-image callers**, all in the engage-SM cluster
`0x40fda–0x41386`, params `{1,2,4,1,1,2,3}`. Only the two param-2 callers (`0x410a2`, `0x41280`) and the one
param-3 caller (`0x41364`) reach the NOP'd branches; **nothing anywhere else in the 1 MB image passes 2 or 3.**
→ the NOPs affect ONLY the ENGAGED/HOLDING engage-SM states.

**No hard-EME/DTC escalation (high confidence, corroborated by both tracers):**
- The state-4 leave path (`FUN_00040d58` → `FUN_00040e74`) is a substate-byte copy with **no DTC/fault call.**
- `FUN_000406ae` (fully re-disassembled) has **no `FUN_0006b9fa`, no DTC path** — its only side effect is the
  conditional `gp-0x35ac` write, which V34 preserves (call retained).
- **State 4 is NEVER persisted into the outer dispatcher state `gp-0x67DC`** (every `FUN_00040d38(n)` call in
  the cluster uses n ∈ {0,1,2,3,5,6,7}, never 4). The `gp-0x67DC`/shadow `gp-0x4C35`/`FUN_0006b9fa` lockstep is
  structurally untouched.
- Redundant genuine-fault coverage SURVIVES: the `gp-0x6cc4`/`gp-0x4D0C` RAM-integrity shadow still catches
  angle-state corruption; the torque-corridor hard DTC (`FUN_00042af8`/`FUN_00043e44`, DTC `0xF00049`) is a
  different domain, unaffected. **V34 cannot mask a condition that would otherwise set a DTC.**

**One correction between the two sweeps (kept, not silently applied):** the substate byte `gp-0x35B5` (which
carries the 2/4/0 distinction) is **not** write-only as the first downstream pass claimed — it has 4 readers
feeding an output struct via a function-pointer table (`0xB7AB4` → `FUN_000512fc`). This does **not** create a
hazard: on a bump V34 makes the decider return the **normal 0**, so that cycle is byte-for-byte a normal
no-fault stay cycle — `gp-0x35B5` simply isn't stamped with the transient "angle-fail." (If that struct is the
live STEER_STATUS source, this also reinforces why the fix should work — the alert value is never produced.)

**Which NOP is operative** (ENGAGED vs HOLDING during a sustained hands-off turn): unresolved — the
ENGAGED↔HOLDING selector `gp-0x67FE` couldn't be pinned (conflicting branch-polarity reads). Moot, because
V34 NOPs both states.

## 4. Efficacy + residual uncertainty (be honest — the road is the arbiter)

**Fix mechanism (structurally confirmed):** the ENGAGED handler `FUN_00041222` gates on the decider return:
`r10==0` (stay) runs the keep-delivering path (`FUN_000405fe` → conditional `FUN_0003d04c(4,0)`); `r10≠0`
(disengage 2/4) commits the substate and SKIPS it. V34's NOPs make a bump→consensus-fail return **0** instead
of **4** → on a bump the handler stays on the keep-delivering path. That is exactly how the fix acts.

**Confidence:** the gentle EME is the decider's angle-consensus disengage — **well-supported** (direct
bump→angle→gate path; reliable mechanical reproduction fits it far better than a stochastic frame glitch; V33's
failure rules out the torque gate). V34 disables both decider gates a bump could plausibly trip.

**Residuals (named plainly):**
1. **`FUN_0003d04c` not fully decompiled** — the actual deliver/status setter. The gate-behavior divergence is
   confirmed; the last hop to the deliver flag / `no_torque_alert_2` write is inferred.
2. **Voter `gp-0x6a62 == 0xffff` frame-glitch sentinel (retained).** Lower probability (needs a sensor/DMA
   frame glitch, not just a bump), but if THAT is the real trigger, V34 will not fix it — that path is a
   genuine dead-sensor fault path and was deliberately left intact.
3. **Physical scale of `gp-0x6cc4`/`0xC6354=4825`** is unpinned on paper (needs a live RAM read).

Given TWO prior wrong guesses (V32, V33) burned on the wrong gate, **a telemetry-instrumented drive (V31T-style,
piggyback `gp-0x6cc4`=`0xFEDF133C` + `gp-0x6a62`=`0xFEDF159E` + the decider substate on CAN 0x660) would
DEFINITIVELY confirm which gate fires and by how much.** V34 is the operator's chosen "build now" path and is
safe to flash; the telemetry pass remains the recommended way to *confirm* (or to set a `gp-0x6cc4` value if a
future cal-side approach is ever wanted).
