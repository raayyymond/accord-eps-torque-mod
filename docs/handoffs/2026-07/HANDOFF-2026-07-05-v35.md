## 1. The method that found it — trace the PHYSICAL cut, not the STEER_STATUS byte

The operator's decisive correction this session: the gentle EME is the **physical** loss of LKAS torque on a
hard turn + bump, NOT the `STEER_STATUS=no_torque_alert_2` CAN byte (that byte is a downstream annotation —
verified this session to be written directly by a saturating counter in the arbitration/ramp cluster
`FUN_00028ea6`/`FUN_0002a30e`, cal `0xC64E2`=5, which is a *report*, not the cut).

The physical cut: the ENGAGED handler `FUN_00041222` commits LKAS delivery each cycle by calling
`FUN_0003d04c(4,0)` @`0x412ae` — but ONLY on the decider "stay" branch:
```
0x41284 cmp r0,r10 ; 0x41286 be 0x4128e     ; decider==0 (stay) -> fall to deliver path
0x41288 jarl FUN_00040e74 ; 0x4128c br 0x412b2 ; decider!=0 -> SKIP 0x4128e..0x412b1 (incl the deliver call)
...
0x412ae jarl FUN_0003d04c(4,0)               ; the keep-delivering commit (skipped on any nonzero decider)
```
The whole project already treats "this commit does not run → LKAS not delivered → cut" as THE gentle-EME
mechanism. **So ANY path that stops the commit is cut-equivalent** — including `FUN_0003d04c` bailing internally.

## 2. The residual gate — `FUN_0003d04c` Gate 7 [V — radare2 v850.gnu, adversarially re-derived]

`FUN_0003d04c` (0x3d04c–0x3d1f4) has 7 pre-gates evaluated BEFORE the delivery-commit switch; bailing any of
them jumps to the return (`0x3d1e2/1e6/1ea/1ee/1f2`) and skips the commit. **Gate 7:**
```
0x3d0a8  ld.hu 29438[r5],r14   ; r14 = cal tp+0x72FE = 0xC62FE = 320 (0x0140)  [px-verified]
0x3d0ac  ld.hu -27230[gp],r16  ; r16 = gp-0x6a5e  (voter AVERAGE sensor-A column torque)
0x3d0b0  cmp r16,r14
0x3d0b2  bh 0x3d0b8            ; cal > gp-0x6a5e -> continue (deliver)
0x3d0b4  jr 0x3d1e6            ; gp-0x6a5e >= 320 -> BAIL = skip commit = TORQUE CUT
```

**This is the same 320 threshold as the decider's `0xC6312` that V33 disabled — but on `gp-0x6a5e` (voter
AVERAGE) instead of `gp-0x6a62` (voter MAX).** Since MAX ≥ AVG structurally, V33 disabling only the MAX gate
leaves this AVG gate as the new binding torque cut. AVG is smoother than MAX → trips on **fewer** events →
**exactly the operator's "frequency reduced but still happens."** Never touched by V32/V33/V34.

### Why the whole lineage missed it
V32/V33/V34 all localized on the engage-SM decider `FUN_00040d58` (the first torque gate found). Nobody had
traced backward from the physical delivery cut into `FUN_0003d04c` — which the V34 handoff itself flagged as
"not fully decompiled" (residual #1). The 320 gate is a *twin*, ~0x3000 bytes away, on the average signal.

## 3. Clean-lever verdict for `0xC62FE` — CLEANER than `0xC6312` [V — whole-image sweep]

- **1 reader** (Gate 7 itself, 0x3d0a8), **0 writers**, **no int/float twin** (320.0f absent image-wide), **no
  word-load overlap** (only neighbor read is 0xC62FC's own bytes at 0x3f9da, unrelated), **no movea/absolute
  build**, **no `FUN_0006b9xx` consistency monitor.** V33's `0xC6312` had 3 readers; this is cleaner.
- NOT the multi-role lockstep class (`0xC6354`, 14 readers/5 roles) that V34 deliberately refused to touch.
- So raising 320→65535 is a clean cal-only edit of the same proven-safe class as V33. `gp-0x6a5e` is
  voter-clamped to 32000, so at 65535 the gate can never bail.

## 5. RESIDUALS / STILL OPEN (be honest — the road/telemetry is the arbiter)

Three prior builds were each confidently wrong. V35 has the strongest evidence of the lineage (validated clean
lever + coherent MAX-vs-AVG mechanism that explains the exact "reduced but present" report), but it is still a
static inference until confirmed on the car. Named residuals:

1. **Gate 5** (`gp-0x4f68 ≥ cal 0xC61EA=4096`) in the SAME function may be a **rate/velocity** signal — a better
   fit for the "+ bump" half of the symptom. Its identity (torque vs rate) is **UNCONFIRMED**, so V35 does NOT
   touch it (fixing what is validated, not guessing). If the EME persists after V35, `0xC61EA` is the next
   lever — pending its own identity + clean-lever check. `gp-0x4f68` is read ~10× in the 0x2bc00 delivery/limit
   region; producer not traced.
2. **The retained `gp-0x6a62==0xffff` voter sentinel** — a bump-coincident DMA-frame glitch can trip it (the 4
   primary coils share bytes in one 8-byte DMA frame, so a single corrupted byte fails the 3-of-4 quorum). It's
   a genuine dead-sensor fault path, deliberately left intact. Lower probability than gate 7 (needs a frame
   glitch, not just torque) but not ruled out.
3. **The last hop** from `FUN_0003d04c`'s skipped commit to the delivered-torque zeroing is inferred, not fully
   decompiled (same residual as `-v34.md` §4).
4. **The independent state-exit** (`gp-0x67FE`/`gp-0x1478` = an ADC/measurement-status byte, fault_id=81) —
   real and survives V34, but it clears the substate to 0 rather than producing the EME signature; weaker.

### RECOMMENDED before flash — the hard evidence three builds lacked
A **V31T-style CAN-0x660 telemetry piggyback** of `gp-0x6a5e` (`0xFEDF15A2`) + `gp-0x6a62` (`0xFEDF159E`) +
`gp-0x4f68` + the deliver-commit result, one hard-turn+bump drive. If gate 7 is the cause, `gp-0x6a5e` crosses
320 at the exact instant delivery drops. This DEFINITIVELY discriminates gate 7 vs gate 5 vs the sentinel
before another byte is flashed.

## 6. SAFETY TRADE (operator's call — named plainly)
With `0xC62FE`=65535 the deliver-commit no longer skips LKAS delivery on high sensor-A (average) column torque
— same class of trade as V33's `0xC6312`: the driver can no longer force an LKAS letdown through this torque
gate (openpilot brake/cancel/override upstream of the EPS still works). Hard-EME (DTC) lockstep, the
invalid-sensor sentinel, and the angle-consensus monitor's other roles are all UNAFFECTED.
