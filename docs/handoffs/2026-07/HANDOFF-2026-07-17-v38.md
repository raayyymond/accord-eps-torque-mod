### Setpoint limit `15360 → 16384` (added 2026-07-18)

The symmetric ± clamp applied to the LKAS setpoint (`gp-0x69ae`) inside `m_steer_torque_arbitration` **immediately before the Q15 LKAS gain `0xC646C`** is sourced from a 9-point LERP whose Y row ships **flat 15360 in every record** — a degenerate curve, i.e. a constant clamp. openpilot `CAR.HONDA_ACCORD` uses `torqueBP=[[0,4096]]` → setpoint max `4096 × -4 = 16384`, so the top **6.25%** of the command range was being clipped. Raising the flat row removes exactly that clip: **+6.71% top-end** (V38: 1670 → 1782 against the 2048 source clamp), observable only above 3840/4096 of commanded torque.

Record format = 40 bytes: `[u16 count=9][9× u16 X][9× u16 Y][u16 pad]`. The X axis (`3200…8320`) is **left stock and guarded** — only the flat Y row moves. The axis input is `gp-0x6a5e` (AVG voter = **driver** column torque), so this is a driver-pushback taper surface Honda shipped flattened.

**Scope — all 8 selector-reachable records.** Across the 16 variant slots (`0xCD000`, stride `0x24`, selector byte `+0x1A`) `gp-0x674e` takes only `{0,1,3,4,6,7,8,9}`. Our A160 resolves via slot 2 (key `TVAA1`) → selector 1 → record `0xE41A8`. Because that slot resolution's HW-ID provenance is not fully pinned down, **all eight reachable records were patched**, so the change lands regardless of how the slot resolves. All eight were byte-identical flat 15360 in stock and only one is ever read at runtime, so the extras are inert. Records 2, 5, 10–15 (unreachable) are **left stock at 15360**.

**Blast radius (whole-image LE32 scan).** Pointer array `0xCB844` is referenced by **exactly one** code site, `0x28FCE`. Bank bases `0xE4180`/`0xE5180` appear **only** inside that array. No aliases, no other consumer. No IEEE-754 `15360.0` exists image-wide in either endianness → **no float twin**, so unlike the corridor/boost walls this edit has no lockstep mirror to keep in step.

**New CRC blocks — first build in this kit to touch them.** The records live in bootloader blocks `[0xE4000,0xE4FFC)` (blk#23) and `[0xE5000,0xE5FFC)` (blk#22). Both were added to `TOUCHED_BLOCKS`, clearing the documented build blocker. The linked-list page fields `walk()` uses to chain blocks sit at `block_start-8/-6` — inside the *preceding* block's range — and are unmodified, so the 49-block chain topology is preserved; only the two trailer words move.

Soft-wall sizing: maximum modeled merged demand is `2048 LKAS + 2560 COMP = 4608`; 5120 leaves 512 counts. The fixed ±`0x2800` and ±`0x2000` clamps do not bind. Nominal governor `0xC6202=4762` leaves only 154 counts; its dynamic schedule (⚠ **motor electrical-angle RATE + energy budget, NOT road speed** — statically resolved 2026-07-17, see below) can still reduce delivered torque under fast steering motion and remains the principal caveat.

> **UPDATE 2026-07-17 — LKAS CAN→motor model firmware-verified against 5 operator review comments** (see `handoffs/2026-07/HANDOFF-2026-07-17-lkas-model-firmware-verification.md`). Net corrections landed in `analysis-2020accord/model/eps_lkas_chain_model.py`: (1) the arb LKAS gain scale is **Q15 `>>15`**, not `>>10` (a prior model draft mis-took an earlier Q10-IIR blend shift); (2) driver-assist is **NOT** summed inside the arbitration function — it is a separate downstream mixer source (LKAS = distribute idx 1); (3) the setpoint IS clipped ~6% at full-scale by the mode-0 const-15360 LERP; (4) the sub-3mph LKAS ignore is **openpilot-side** (`minSteerSpeed`/`STEER_GLOBAL_MIN_SPEED = 3 mph`) + an EPS `LOW_SPEED_LOCKOUT` status — no firmware pipeline speed gate; (5) the governor is **computed** `MIN(4762, motor-rate LERP, energy budget)` with **3 consumers** and a diagnostic override, and its adaptive taper is keyed to **motor angular rate, not road speed**.

V37 guards retained: `0xC64B4/B5/B6/B7/B8=0xFF`, `0xC61C0/C2/C4=0xFFFF`. Thus gentle `STEER_STATUS=4` and DTC-0x49 counter B remain disabled, including V37's accepted `0xC64B8` arbitration side effect.

## Lockstep-slew question — CLOSED 2026-07-18 (the premise was wrong)

The carried-over `[OPEN]` said the +6.71% "scales a pre-existing *actual lags predicted* error term against the `±5/1024` threshold." **That characterization was incorrect**, and it manufactured a concern that does not exist.

**What the `±5/1024` compare actually is.** At `0x4463a`:

```
0004462a: ld.h  -0x6af6[gp],r7    ; INT wall
00044636: mulf.s r9,r1,r2         ; r1 = 0x3A800000 = 1/1024  -> r2 = wall/1024
0004463a: subf.s r2,lp,r10        ; r10 = float_twin - wall/1024
0004463e: movhi 0x3ba0,r0,r7      ; +5/1024
00044646: movhi -0x4460,r0,r14    ; -5/1024
```

Both operands are **same-cycle redundant computations of the same bound in two datatypes** — `gp-0x6af6` written by `s_motor_torque_rate_shaper` (`0x43a7e`/`0x43e38`; a scan of `-0x6af6` returns exactly 5 sites total) vs the float twin `lp` built in `FUN_00043e44` from the float mirrors `0xC6598/A4/AC/C4`. It is an **int-vs-float lockstep**, not a prediction with lag. `memory/reference/firmware/reference_accord_corridor_lockstep.md` already had this right.

**The setpoint is not an operand of the tolerance.** `FUN_00043e44` never reads the setpoint `gp-0x69ae` nor the gain cal `0xC646C` (tp offset `0x746c` is absent from its read set). It consumes the merged command `gp-0x6acc` as an **input**.

> ⚠ **Correction made during this analysis.** A first pass read the `±8.0` compare on `gp-0x6acc` (`0x44696`) as a *gate* that zeroes the term **below** threshold — concluding the setpoint was excluded from the math entirely. **That polarity was backwards.** `trfsr` sets Z on TRUE and `be` branches on TRUE, so the **out-of-range** case is the one that zeroes. Confirmed against the unambiguous reference at `0x43eda`–`0x43f1e`: the identical shape applied to `gp-0x4f60` (driver column torque) with a `±25.0` threshold — a plausibility **sanitize** at ±25600 counts. So `|gp-0x6acc| > 8192` → zero; below → **kept**. V38's 4342 counts is in range and **is** kept.

**The correct reason the raise is safe** — two independent arguments:

1. **Both sides move together.** Every tolerance in this function compares the function's own **float re-derivation** against the **integer shaper's stored result** for the same quantity (flag 1: float bound vs `gp-0x6af6`; flag 2 vs `gp-0x6b00`; flag 6: float `cmd_final` vs `gp-0x6b98`). Raising the clamp translates both sides equally — it does not open a gap.
2. **The per-cycle slew is bounded upstream, independent of the clamp.** `gp-0x6acc` has exactly two writers (both in `m_post_governor_torque_comp_add`/`FUN_000456a4`; the `0x45932` debug path is dead — its enable cal `tp+0x74ba` reads `0x00` in stock) with **no rate limit**. The limit is one stage up, in `m_motor_torque_governor` writing `gp-0x6ace`: step `= (cal × Q15)>>15` with cal `0xC6206`=**512** or `0xC6208`=**205**. **That step does not depend on the setpoint clamp value**, so a raised clamp cannot increase the rate of change — it only extends how many cycles the ramp runs.

⇒ **A faster or larger slew cannot consume lockstep margin.**

### Trip structure (newly characterized, and it corrects the record)

Seven plausibility flags, weights 1/2/4/8/16/32/64 (`0x4464e`, `0x44672`, `0x44794`, `0x447da`, `0x44866`, `0x448ee`, `0x4491e`), summed at `0x44926`–`0x4493a` → **max 127**, against a threshold of **128.0** (`0x44a26`). *No single-cycle combination can trip.* The trip is forced by a debounce SM (`gp-0x3540`/`gp-0x3550`): any flag integrates `0.001`/cycle to `0.01` (**≈10 cycles ≈ 0.1 s @100 Hz**, decay `0.0005`), then adds **1024.0** → 1151 > 128.

The trip calls the DTC setter:

```
00044a4c: jarl 0x000462e6,lp
FUN_000462e6:  movea 0x1d,r0,r6 ; jarl 0x00016de6  =>  FUN_00016de6(0x1D, 0x3f1b, 1, 1)
```

This resolves a contradiction between two kit memories — and the resolution **raises** the stakes. `corridor_lockstep.md` called this a "hard shutdown (DTC 0xF00049)"; `override_snap_state_machines.md` called it "REPORT-ONLY — does NOT gate torque." **`corridor_lockstep` is right; `override_snap` is wrong and is now retracted in place.**

There are **two** monitors, and the one `override_snap` named by accumulator is the hard-shutdown one:

| | Monitor 1 | Monitor 2 |
|---|---|---|
| function | `FUN_00042af8` (shaper) | `FUN_00043e44` (watchdog) |
| accumulator | `gp-0x3564` int, +10/cyc, thr 100 | `gp-0x3550` float, +0.001/cyc, thr 0.01 |
| trip | `FUN_0004613e` → `FUN_00016de6(0x1c,…)` | `FUN_000462e6` → `FUN_00016de6(0x1d,…)` |

`gp-0x3564` is traced at instruction level **to motor-off**: `FUN_00016de6` → `FUN_0001611e` (bits `0x41` gate) → `FUN_00018738` → `gp-0x685c`=1 → `FUN_00018bc0` (`gp-0x3ef8`=1) → `FUN_00019f7c` → `gp-0x67fa`=8 → `FUN_0001a16a` → `FUN_00045608(3,0,0x8000,0x8000)` **motor off** → `gp-0x3ee8`=1, **power-cycle to recover.** This is the V25/V26 brick mechanism.

## What V31 teaches V38 — scaling audit (operator-directed 2026-07-18)

V31 is the build that resolved **both** the hard and soft faults at 2×, so it is the reference for whether V38's 4× scales those fixes correctly. Every cal below read from the actual plain images.

### V31's mechanism, and V38's inheritance of it

V31's fix was **not** to raise any state-machine threshold (that was V19's rejected approach). It was to **floor the soft-EME bound above the max command** so the integrator `gp-0x3570` can never wind on `(command − bound)`: with all three bound arms collapsing hands-off (corridor gated off at `0xC6156`=9216, IIR decayed, boost the only arm ON at authority≈0), flooring **boost** makes the fixpoint self-stable — authority stays ≈0, so boost is never latched off and the SMs never arm.

**V38 inherits this correctly.** Since the integrator is *additive*, the right invariant is **absolute** margin, and V38 preserves it exactly:

| | V31/V37 (2×) | V38 (4×) |
|---|---:|---:|
| max merged (clamp-sum) | 3584 | 4608 |
| corridor / boost wall | 4096 | 5120 |
| **margin (the invariant)** | **+512** | **+512** |
| int/float mirrors exact at 1/1024 | ✓ | ✓ |
| all four tables flat | ✓ | ✓ |

All SM thresholds, the LERP_B envelope cal `0xC6664`, and the fault-SM gate `0xC64A4` are **unchanged from stock** in both — verified byte-wise.

### 🛑 RETRACTED: the "V38 spent all its SM margin" alarm was a DOMAIN ERROR

An earlier version of this section compared the LKAS source clamp to SM1's threshold and the setpoint clamp to SM2's threshold, reported both margins as `+1024 → 0`, and flagged V38 not-flash-ready. **Both were cross-domain comparisons. Both alarms are FALSE and retracted.**

**SM2's operand is AUTHORITY, not the setpoint.** `r13` traced:

```

000432ee: sar   0xf,r10           ; >>15 signed
00043286: subr  r0,r24            ; absolute value

So `0xC6422`=16384 is an **authority-domain** threshold; V38's 16384 is a **setpoint-domain** clamp. Unrelated numbers that happen to be equal. The `~15360` in `override_snap` is `16384 × 1024 / 1092 = 15363.8` — the **integrator-domain** equivalent of the threshold, which that memory conflated with the setpoint clamp. Arming requires `|gp-0x3570| ≳ 503,000,000`, reachable only by sustained winding that the bound floor prevents.

**SM1's 2048 is a qualifier inside a driver-opposition AND.** `0xC61DE` has exactly one real reader (`0x43360`; other `71de` hits are branch-target substring false positives). The arm chain at `0x43670`–`0x4368c`:

```
00043670: cmp r2,r15  / bnh -> NO ARM     ; velocity arm
00043674: cmp r1,r14  / bnh -> NO ARM     ; r1 = 0xC61DE = 2048 magnitude qualifier

The decisive term is the product test: SM1 arms only when the command **opposes the driver's hand torque**. It is a driver-override detector, and 2048 is a magnitude qualifier *within* it — not clearance V38 consumed. ### 🛑 INVESTIGATED AND REJECTED (2026-07-18) — `0xC6202` stays stock

The open items were closed; every one came back against the change.

**1. It buys nothing where it matters.** Nominal **4762 > max command 4608** (4342 actual) — **the governor does not bind at nominal.** Raising it changes nothing in normal operation; it only acts in the **tapered** regime (`MIN(nominal, motor-rate LERP, energy budget)`), i.e. when the motor is moving fast or the energy budget is stressed — *which is the protection working.* ⚠ This corrects this handoff's own framing: "governor headroom collapsed 7.6×" is a true observation with a **wrong implication**. It is not a fault risk; it is Caveat 1 restated.

**2. `gp-0x4f64` is a SHADOWED variable whose mismatch fault is HARD-ELIGIBLE.** Every write checks the live value against a shadow at `gp-0x448a` first:

```
0007c2d2: ld.hu -0x4f64[gp],r16   ; live
0007c2da: ld.hu -0x448a[gp],r7    ; shadow
0007c2de: cmp r7,r16 / bne -> jarl 0x0006b9ee

FUN_0006b9ee: movea 0x17,r0,r6 ; fault index 0x17 -> jr 0x0006ce7c
```

Fault `0x17`: `record[+8]` = `0x2D01`, `& 0x41` = **1** → **hard-fault-eligible**, same class as the lockstep monitors (motor-off, power-cycle recovery).

**3. It feeds a limp/fallback path that writes the torque command directly** (`0x6e0f2`, `0x6e1ca`): `gp-0x4f64 × cal 0xC7C3C(424)` → `st.h ... -0x6b98[gp]`. Raising it raises **limp-mode torque**.

**4. The cal→variable chain is UNVERIFIED.** `0xC6202` is read at `0x7b06a`; `gp-0x4f64` is written at `0x7c2e2`/`0x7c3b4`/`0x7c47c` — **~4.7 KB apart** through float math in one huge function. The claim that `0xC6202` determines `gp-0x4f64` originated from a subagent and **could not be confirmed**.

**Verdict: `0xC6202` left stock in V38.** Revisiting requires closing all four, staying well under the 10240 monitor ceiling, and shipping as **its own road-validated build** — never bundled with a reach change.

### Why NOT to code-cave SM1 / SM2 / the governor

- **SM1/SM2: there is nothing to fix.** Both "margin" problems were domain errors. Disabling them removes the **driver-override snap** — the mechanism that lets the driver win when fighting the wheel. On a steering system that is a primary safety function.
- **The governor is the motor's thermal/energy protection.** It is `MIN(nominal, motor-rate LERP, energy budget)`; the dynamic terms prevent overheating. Removing it risks **hardware damage** — a worse class than a recoverable fault. Raising the nominal cap keeps the dynamic protection intact; deleting the governor does not.
- **Code caves are this kit's worst-performing change class.** V24 and V27 both used trampolines at `0xC4E00`; both faulted. **Every build that has succeeded since V29 has been cal-only.** The lockstep monitors exist specifically to catch code-path divergence, so injected code is the most likely thing to trip them.

**Recommendation: pursue the cal-only `0xC6202` raise; do not cave.** If a cave ever proves unavoidable it should be its own build with its own road validation, never bundled with a 4× reach change.
