## 1. Why 0xFFFF fully disables the torque disengage [V — radare2 v850.gnu]

The gate lives in `FUN_00040d58` (engage-SM decider), ENGAGED (param 2) / HOLDING (param 3) branches:

```
0x40dc6  ld.hu -0x6a62[r4=gp], r14   ; r14 = gp-0x6a62 (voter MAX-of-5 coils, rising-edge unfiltered, clamp 32000)
0x40dca  xori  0xffff, r14, r0        ; test == 0xffff (invalid-sensor sentinel)
0x40dce  be    0x40dfc                ;   invalid -> disengage(2)   <-- LEFT INTACT (fault path)
0x40dd0  ld.hu  0x7312[r5=tp], r16    ; r16 = cal 0xC6312            <-- V33 makes this 65535 (was 320)
0x40dd4  cmp   r16, r14
0x40dd6  bnl   0x40dfc                ; gp-0x6a62 >= threshold (UNSIGNED) -> disengage(2)
```

The threshold is loaded with **`ld.hu` (unsigned 16-bit)** and compared **unsigned** (`bnl` = branch-if-not-lower
= CY==0). Datatype max = `0xFFFF` = 65535. Since the voter clamps `gp-0x6a62` to **32000** (`0x7D00`), for every
attainable torque `gp-0x6a62 < 0xFFFF` is **always true** and `gp-0x6a62 != 0xffff` is **always true** ⇒ the
stay-engaged condition always holds ⇒ **the torque-magnitude disengage can never fire.** Param 1 (engaging)
uses the same cal as a "deliver iff `gp-0x6a62 < 0xC6312`" gate — at 65535 that too always allows delivery.

**Deliberately retained:** the separate `gp-0x6a62 == 0xffff` **invalid-sensor sentinel** (0x40dca/0x40dce) is
a torque-SENSOR-FAULT path, not the hard-turn gentle EME. It still disengages LKAS if sensor A returns the
invalid marker (correct — you can't trust hands-off control with a dead torque sensor). Maxing the threshold
does not touch it.

## 3. ⚠ SAFETY TRADE (operator chose this — name it plainly)

With `0xC6312 = 65535` the driver can **no longer take steering authority from LKAS by pushing on the wheel
through the sensor-A torque gate** — at any force. The operator has judged the gentle-EME trigger scenario
(LKAS momentarily letting go on a hard sustained hands-off turn) to be always-unsafe and worse than losing
this specific override gate. **openpilot-side disengagement (brake / cancel / the driving stack's
steering-override detection) is upstream of the EPS and is UNAFFECTED**, so a driver override path still
exists. Hard-EME (DTC 0xF00049) lockstep and the invalid-sensor sentinel are both intact.

## 4. ADDRESS-LABEL CORRECTION (verified, then fixed in prior docs)

The prior gentle-EME docs disagreed on where `0xC6312` is read. **Resolved with radare2 `v850.gnu` this
session, at the raw-byte level:**

- **Cal `0xC6312` reads** (`ld.hu 0x7312[r5=tp]`, bytes `e53f1373`/`e5871373`): **`0x40db8 / 0x40dd0 / 0x40df4`**.
- **`gp-0x6a62` value reads** (`ld.hu -0x6a62[r4=gp]`, bytes `e4779f95`): **`0x40dae / 0x40dc6 / 0x40dea`**.

The two sets use **physically different base registers** — r5 (tp) for the cal vs r4 (gp) for the RAM value —
decoded directly from the instruction `reg1` field, so this is **not** a gp/tp confusion nor a Ghidra-vs-r2
base shift (a base shift would move both by the same round offset; here they differ by the 10-byte
value-load→cal-load spacing AND use different registers). The V32 handoff §1 already had it right
(`0x40db8/dd0/df4`). **Fixed the wrong `0x40dae/dc6/dea` labels in:** `HANDOFF-2026-06-30-sensorA-identity-
gate-scale.md` (§1 + key-address table), `builds/v18_v49/build_v32_tva.py` docstring, and the engage-SM agent memory
`reference_accord_lkas_engage_sm_disengage_trigger.md`.

**⚠ Tooling note:** radare2's **default `v850` plugin mis-decodes** this V850E2 code (it renders the `ld.hu`
cal/value loads as bogus `setf`/`xori`). Use the **binutils-based `v850.gnu`** decoder
(`r2 -a v850.gnu` / `e asm.arch=v850.gnu`) for V850 work here — same family of quirk as
`reference/tooling/reference_rizin_ghidra_v850_quirks.md`. (Ghidra was not usable this session: the release download is
GitHub-hosted and blocked by the cloud environment's proxy; radare2 installs via apt. JDK 21 is present, so
headless Ghidra would work if GitHub is ever allowlisted.)

## 5. Whole-image enumeration that backs "3 readers, nothing else" [V — radare2]

- **`13 73`** (ld.hu disp `0x7312`): exactly 3 hits → the 3 cal readers. No other reads.
- **`12 73`** (ld.h/st.h disp `0x7312`): 12 hits, all `cmov` instructions (coincidental bytes) → **0 writes**.
- **`12 63`** (movea imm `0x6312`, absolute-address build): 8 hits, all straddle/data/sld.b/unaligned → none real.
- **`11 73`** (disp `0x7310`, would word-overlap 0xC6312): 2 hits, both `ld.hu 0x7310[r5]` = halfword reads of
  the neighbor `0xC6310`=1600 (engage-refuse gate), don't reach 0xC6312.
- No `tp+0x73xx` block-base pointer is ever constructed (53 `0x7300`-imm sites decoded → none is a movea/addi
  block pointer), ruling out indexed access.
