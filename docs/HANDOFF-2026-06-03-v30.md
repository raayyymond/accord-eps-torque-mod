## Corrected wall model (this session — both monitor fns re-traced on stock `code.bin`)

```
gp-0x6af6 = max( dir_corridor[cal 0x774e],  velocity/cmd-envelope IIR[gp-0x3574],  boost[cal 0x7760] ) × polarity
```
a **three-way max**, with arm identities/ranges now resolved:

| arm | what it is | input | output range |
|---|---|---|---|
| **dir_corridor** | velocity-gated magnitude limit (THE soft-EME corridor) | velocity (X=±8192) | flat ±1024 stock / **±4096 V30** |
| **IIR envelope** `gp-0x3574` | IIR(α=10) of a LERP3 envelope. **NOT driver torque** (that's `gp-0x69ca`). | LERP3 index `gp-0x4f60` — **identity CONTESTED**: column/motor angular velocity (2 memories, [STRONG]) vs rate-limited LKAS command (2 tracers, via the un-walked `gp-0x6b50`). | hard-capped **0x3000 = 12288**; typical ~512–2048 |
| **boost** `0x7760` | turn-rate boost (LERP) | `gp-0x6ac2` = **|steering angular rate|** ∈ [0,13000] (encoder→`gp-0x4f50`) [EVIDENCE] | [0, **2048**]; saturates at rate > 1100 |

- **Both monitors** compare the float twins `gp-0x6db0`/`gp-0x6db8` (×1024) vs the int walls
  `gp-0x6af6`/`gp-0x6b00`, window ±5 LSB → ≥128.0 → `FUN_000462e6(0x3f1b)` hard shutdown (DTC `0xF00049`).
- **Consequence of the ranges:** the IIR arm (≤12288) can far exceed the corridor and dominate the wall
  when active; the corridor only sets the **floor** in the quiet regime (IIR + boost both small). Boost
  ceiling (2048) = the old V29 corridor.

### The command being compared (`gp-0x6acc`) and the COMP term

`gp-0x6acc` = `governed_LKAS + COMP_TORQUE`, read by the shaper at `0x431c4` (before the other mixer lane
`gp-0x6afe` reconverges at the output):
- `governed_LKAS` — clamp-bounded by `0xC61B4` → ≤ **1024** (V18 2×). The 2× torque is V18's GAIN
  (`0xC646C`), which is **monitor-independent** (absent from the wall computation) and flashed+road-validated.
- `COMP_TORQUE` — a **driver-override compensation** added in `FUN_000456a4` (post-governor). Gate:
  `LERP1(|driver torque gp-0x69ca|) < gp-0x6ac0 (LKAS cmd)` — engages only at high driver torque.
  Magnitude = `MIN(|(gp-0x6ac0 − LERP1)×3072>>10|, LERP2_cap)`, ceiling `0xC67D8` table = **2560**.

Worst-case `|gp-0x6acc| = 1024 + 2560 = 3584` → V30 corridor 4096 contains it with ~512 margin.

## ⚠ SAFETY TRADE (operator's call — name it plainly)

The integrator `gp-0x3570` (the soft-EME ramp; the override SMs `gp-0x6960` arm off it) winds up on
`(gp-0x6acc − wall)`, `wall = max(corridor, IIR, boost)`. With the corridor a **4096 floor**, the worst-case
command (3584) is below the wall in **every** regime → **the integrator effectively never winds up → the
corridor/SM soft-EME cutback is functionally inert.** That is the intent (hold 2× LKAS, no LKAS drop when
the driver adds torque), but it means the 2× is held even when the driver overrides — the "fights the
driver" regime `reference_accord_driver_override_plausibility_eme` cautioned about. V30 does **not** edit any
monitor *code* and the **hard-EME (DTC) lockstep is fully intact** (corridor matched int↔float); it sizes the
corridor. The proportional alternative is V19's SM-gate rescale.

**Residuals [I]:**
1. **Comp magnitude uncertain → 4096 may be oversized.** Ceiling is 2560 but the realized term
   `(gp-0x6ac0 − LERP1)×3072>>10` may be far smaller (the gate needs `LERP1 < gp-0x6ac0`, which are close).
   To right-size: trace `gp-0x6ac0`'s range in `FUN_00041464`, then corridor = `1024 + realized_comp`.
2. **If the felt EME is the torque-sensor PLAUSIBILITY dropout** (the voter path, not the integrator), V30
   won't fix it (that mechanism doesn't run through the corridor) — same caveat as V29.
3. **IIR-arm input identity unresolved** (velocity vs command) — doesn't affect V30's safety (the IIR arm is
   untouched and matched int↔float) but matters for the full envelope picture. Resolve by walking `gp-0x6b50`.
