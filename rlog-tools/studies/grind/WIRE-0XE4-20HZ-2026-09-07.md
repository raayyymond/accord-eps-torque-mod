# Is the 18–22 Hz grind #1 line IN the 0xE4 steer command, or only RUNG BY it? — V282 wire read

Subagent `wire`, 2026-09-07. Script `wire_0xe4_20hz.py` (this folder; full output
`_scratch/wire_0xe4_20hz.txt`). **Analysis only: builds nothing, sends nothing.**

Routes **r39 / r3a / r3c** (all V282), caches `analysis-2020accord/_scratch/cache/v280/*.npz`, loaded
through `creep20_loop_id.load()`. "Engaged" = **LATERAL** engaged (0x18F `STEER_CONTROL_ACTIVE` AND
0xE4 `STEER_REQUEST`, src 129) throughout. Episode detection is `grind1_census_v282.py`'s recipe
unchanged (2 s windows / 0.5 s step; present = 15–26 Hz peak prominence ≥ 8 AND bar 18–22 ≥ 40 raw;
episode = contiguous ≥ 0.5 s present run inside an engaged run) — 85 usable V282 episodes here.

> 🛑 **CORRECTION OF RECORD, 2026-09-07 (team-lead), BEFORE YOU READ SECTIONS 4, 5b AND 7.**
> `GI.simulate` is an **OPEN-LOOP replay mirror**, not a closed-loop simulation. It drives the PID with
> the **logged** 0x18F wheel rate as the feedback operand and the **logged** 0xE4 as the command
> (`wire = C20.up1k(g["wire"][seg]) ; x = -wire`); there is no plant and no loop closure. Therefore
> every ratio in sections 4 and 5b is **the SHARE of T's 18-22 Hz content attributable to one input
> path, with the other input held at what actually happened** — it is *not* a prediction of the
> closed-loop consequence of removing the trigger. In a lightly damped **stable** mode the ring
> amplitude scales with whatever excites it, so cutting the excitation would also shrink the feedback
> term, and the true closed-loop benefit is **larger** than these shares. If instead the mode were
> self-sustained (damping ≤ 0), no filter on the trigger could cure it at all. **Which of those two it
> is, is settled in the second addendum.** Read "0.909" as *"the command path contributes 9 % of the
> PID sum's 20 Hz content"*, never as *"a filter can only remove 9 %"*.

low-pass; it emits a 20 Hz stairstep command held for 4 frames and sent at 100 Hz; Honda's EPS does
exactly what it is told."*

Measured on the raw per-frame values, on the 0xE4 stream's own dejittered clock (fs = 1/P = 99.55 Hz).
Nothing is resampled anywhere in this path.

### 2a. Pooled Welch PSD, engaged, nperseg 512 (0.195 Hz bins), raw counts²/Hz

A **discrete, narrow line at 20.03 Hz**, present on every route, several times the local floor. This is

### 2b. Fine line frequency — same estimator on every stream (episode medians)

| route | cmd (0xE4) | bar (0x18F) | wheel rate (0x18F) | angle (0x14A) | T (427 tap, 0x1AB) |
|---|---|---|---|---|---|

Every stream, including the command, lands on the same line to within 0.25 Hz, and the pooled per-episode

estimates is weak (r = 0.47 / 0.13 / −0.13, median |Δf| 0.06–0.21 Hz) — the short-window estimates are
too noisy to demonstrate frame-by-frame tracking, so read this as *"the command's line coincides with the
car's"*, not as *"it provably follows it."*

### 2c. Is the command's line present when the car is not grinding?

18–22 Hz amplitude, raw counts, median over ≥ 1.28 s runs:

| route | cmd, episode | cmd, non-episode | ratio | bar, episode | bar, non-episode | ratio |
|---|---|---|---|---|---|---|
| r39 | 36.0 | 12.0 | **3.00** | 73.1 | 24.9 | 2.94 |
| r3a | 38.5 | 7.1 | **5.45** | 101.7 | 22.4 | 4.53 |
| r3c | 23.4 | 8.8 | **2.65** | 69.1 | 28.4 | 2.43 |

The command's 20 Hz content rises and falls **with the car's**, route by route, at the same ratio. A
fixed openpilot clock artefact would not do that.

### 2d. Is there a step-impulse comb at the command update rate?

**No, and there cannot be one in band.** The command updates essentially every frame (§1a), so the
zero-order hold's first spectral image sits at 1/P ≈ 99.5 Hz ± f — above the 50 Hz Nyquist of every
instrument on this car. The only peaks in 30–49.5 Hz are at **39.86 Hz** (and 40.05 / 39.67), i.e. the
**second harmonic of the 19.93 Hz line**, not a comb. Folding mean |Δcmd| by frame index mod N gives a
relative spread of 0.001–0.055 across N = 2, 3, 4, 5, 10 with **no** systematic excess at N = 5.

🛑 The impulse train is real, but it lives **inside the EPS at 1 kHz, at 100 Hz and its harmonics** —
each command frame is held for 10 PID ticks, so 32·Δsp arrives on 1 tick in 10. That is the D-clamp
mechanism the STATE box already describes. It is **not** a 20 Hz phenomenon and it is invisible to any
50/100 Hz instrument.

conclusion below (§3b, §4, §5) is built without phase.

### 3b. The openpilot angle→command path [EVIDENCE: source; BELIEF: the gain model]

Read from `openpilots/StarPilot` (`selfdrive/controls/lib/latcontrol_torque.py`,
`latcontrol_vehicle_tunes.py`, `common/pid.py`, `selfdrive/controls/controlsd.py`,
`opendbc_repo/opendbc/car/lateral.py`):

```
measurement     = -VM.calc_curvature(rad(CS.steeringAngleDeg - angleOffsetDeg), vEgo, roll) * vEgo**2
error           = setpoint - measurement                 # setpoint is the 20 Hz model path: DC at 20 Hz
error_with_lsf  = error * (1 + lsf/current_kp)           # lsf = (interp(v,[0,10,20,30],[12,10.5,8,5])/max(v,.3))**2
output_lataccel = pid.k_p*error_with_lsf + i + ff        # ff += friction*LAF*clip(error_with_lsf/0.30, -1, 1)
output_torque   = output_lataccel / LAF
apply_steer     = round(output_torque * STEER_MAX)       # STEER_MAX 4096, then rate-limited to 123/frame
```

Three structural facts, all EVIDENCE from the source:

1. **The measurement is `CS.steeringAngleDeg` at 100 Hz with no low-pass anywhere** on the path from the
   CAN frame to `error`. The observer's core intuition — *no filtering* — is correct, just about the
   feedback path rather than the command staircase.
2. **`PIDController.k_d` defaults to 0 and is never set**, so the `error_rate=-measurement_rate` term
   (itself 2 Hz-filtered) is **inert**. openpilot contributes no derivative action at 20 Hz.
3. `controlsd` overwrites `pid._k_p` with the `SteerKP` toggle every frame — 0.600, matching the kit's
   measured `p/error = 0.600`.

Predicted small-signal gain, `Gpred = STEER_MAX·(1 + lsf/current_kp)·(k_p/LAF + friction/thr)·(π/180)v²/(SR·L)`,
with SR 16.1, wheelbase 2.83 m, k_p 0.600, SteerFriction 0.212, threshold 0.30:

| route | v p50 | LAF | lsf | Gpred (flat k_p) | Gpred (KP ladder) | **G measured** | meas/pred | angle 18–22 amp (deg) | coh |
|---|---|---|---|---|---|---|---|---|---|
| r39 | 7.7 | 2.11 | 2.00 | 396 | 126 | **831** | 2.10 | 0.032 | 0.51 |
| r3a | 7.7 | 4.00 | 1.98 | 343 | 109 | **681** | 1.98 | 0.050 | 0.49 |
| r3c | 6.8 | 3.60 | 2.58 | 339 | 87 | **823** | 2.43 | 0.032 | 0.44 |

⚠ `current_kp` is genuinely ambiguous in the source (the flat toggle replaces `pid._k_p`, which is then
read back through a speed interpolation), so both readings are priced. The measured gain sits ~2× above
the flat-`k_p` prediction. **This is an order-of-magnitude agreement, not a validated model**: the 0x14A
angle quantises at 0.1 deg, which is 2–3× the 18–22 Hz angle ripple itself, so the angle auto-spectrum is
inflated by quantisation noise and the H1 gain estimate is biased *down*. What the row supports is only
that **an unfiltered 100 Hz angle→command path exists and is of the right size to explain the command's
20 Hz line** — not its exact gain.

## 5. Candidate EPS-side setpoint filters, simulated on the real staircase [EVIDENCE]

The setpoint path is a zero-order hold, 10 PID ticks per command frame, with **no memory anywhere from
the CAN byte to the error** (STATE 2026-09-06). Two candidate code edits, both applied before the demand
chain:

- **IIR** — `sp += α·(cmd − sp)` each 1 kHz tick, `α = 1 − exp(−2π·fc/1000)`.
- **LERP10** — ramp linearly from the previous frame's value to the new one across the 10 ticks. This is
  exactly a causal 10-tick moving average of the staircase, so it costs **no extra frame of buffering**.

### 5a. On the command itself, pooled over all engaged 0xE4 frames of the three routes

| filter | α | cmd 18–22 amp | vs staircase | per-tick kick (raw) | vs staircase | added group delay | phase @ 2 Hz |
|---|---|---|---|---|---|---|---|
| staircase (as flown) | — | 17.91 | 1.000 | 17.63 | 1.000 | 0 ms | 0° |

## 6. Alias check [EVIDENCE]

The 0xE4 stream in the rlog is **not a sampling of a continuous signal**: every transmitted frame is
logged, and the logged value **is** the value the EPS receives. The clock is 10.042–10.045 ms (99.55 Hz).

- **CAN exclude:** that the command's 20 Hz line is a logging or resampling artefact. It is measured on
  the raw per-frame values, on the stream's own dejittered frame counter, with no resampling anywhere.
- **CAN exclude:** that a "true" 80 or 120 Hz command component folded down to 20 Hz. openpilot emits one
  value per frame; anything it computed above 49.8 Hz was already folded by **its own** 100 Hz rate
  before transmission. The EPS receives the same folded sequence we log. **The command IS the 100 Hz
  sequence** — there is no hidden higher-frequency command the EPS can see and we cannot.
- **CANNOT exclude, and this is different:** an 80 or 120 Hz *mechanical* line folding to 20 Hz on the
  **0x18F rate / 0x14A angle** streams, where the sensor is continuous and the 100 Hz CAN frame genuinely
  is a sampling. That is TASK 5's open question and this study does not touch it.

Consequence for attribution: the 20 Hz **in the command** is real at 20 Hz. The 20 Hz **on the wheel
streams** still carries the fold risk — so §4's split ("9 % command, 63 % feedback") is a statement about
the 18–22 Hz *band as the EPS's own 1 kHz arithmetic sees it through those streams*, inheriting whatever
TASK 5 eventually concludes.

## 7. Verdict — in the command, or rung by it?

**Both, and the wire says which one matters.** The 20 Hz **is** in the 0xE4 command: a discrete
20.03 Hz line, 5.6–7.4× above its own noise floor, with a second harmonic, sitting within 0.05 Hz of the
bar / rate / angle / 427-tap line and swelling 2.7–5.5× exactly when the car grinds. But the outside
observer's *mechanism* is falsified in every specific: the command is not a 20 Hz stairstep held for four
frames — it changes on 92 % of frames, at a full 100 Hz, and there is no frame-locked comb anywhere.
The line gets into the command a different way, and the openpilot source says how: `LatControlTorque`
derives its measurement from `CS.steeringAngleDeg` at 100 Hz with **no low-pass at all**, so the wheel's
own resonance is fed straight back out as command ripple with a gain of order several hundred counts per
degree. The command's 20 Hz is an **echo of the car, re-transmitted**, not an independent excitation. And
it is a small echo: delete 100 % of it in the 1 kHz mirror and **91 %** of the delivered 18–22 Hz torque
survives, whereas low-passing the EPS's own rate feedback leaves **37 %**. Grind #1 is rung by the
command's broadband step content and sustained by the EPS's rate loop; it is not carried by the command's
20 Hz line.

**What an EPS-side setpoint filter could fix:** the **excitation**. Every dose here cuts the
per-1 kHz-tick impulse into the D term by **10–17×** and the D-clamp binding duty inside grind episodes
from 1.81 % to **0.30–0.89 %** — attacking the same mechanism V287's clamp attacks, but at the source
rather than at the limiter, and **without clipping the feedback derivative**, which is precisely what
failed adversary B on V287 rev 1. It would also blunt the rate-limited 123-count command steps that the
census found enriched 2.80× at episode onsets (the first addendum shows those *are* the slew cap).

🛑 **What the 8–13 % figure is, and is not.** It is the fraction of T's 18–22 Hz content that the
**command path contributes to the PID sum** in an open-loop replay where the logged wheel rate is held
fixed. It is **not** a closed-loop ceiling. Whether a filter on the trigger can do better than its
direct share turns entirely on the sign of the mode's damping: if the 18–22 Hz mode is a **stable rung
bell**, cutting the excitation cuts the ring that feeds the 63 % feedback term too, and the closed-loop
benefit exceeds 13 %; if the mode were **self-sustained**, no trigger filter would cure it at any dose.
**The second addendum settles which.** What is unconditional either way: the filter cannot break the
openpilot echo, which closes outside the EPS, and every millisecond of setpoint lag is phase spent from
openpilot's own outer-loop margin (11.3° at 2 Hz for IIR 10 Hz, 3.2° for LERP10).

## B5. Corrected verdict

**Grind #1 is a RUNG BELL, not a self-sustained oscillation.** 97.6 % of V282 episodes decay after
their peak and only 2.4 % do not; the effective damping ratio at 20 Hz is ζ ≈ 0.026 (0.035–0.041 for
bursts) — small but firmly positive; real episodes decay faster than a stationary same-spectrum
surrogate; nothing rails; and the excitation leads the envelope by 100–340 ms. The transient
amplification is real (real rises beat the null at p < 0.0001 on r39), which is what makes bursts look
explosive, but a mode that collapses in 166–227 ms once the drive stops is a bell being struck, not a
loop going unstable.

**Therefore the "8–13 %" is a LOWER BOUND on the closed-loop benefit, not a ceiling.** Because damping
is positive, cutting the excitation also shrinks the ring that feeds the 63 % feedback term. How much
more cannot be quantified from these logs — that needs a validated plant model, which the record
explicitly says it does not have to gate precision (`CREEP-20HZ-LOOP-ID` marks the absolute margins
BELIEF, plant coherence 0.3–0.6). **What I can state is the direction and the floor.**

**One structural point in the filter's favour that was not in the main report.** A setpoint-path filter
is a **PREFILTER**: it shapes the reference into E = 32·sp − fb and **does not appear in the rate loop's
loop transfer at all**. The loop gain and phase margin from fb to output are byte-for-byte unchanged, so
GATE 2 for the EPS rate loop is untouched by any of these doses. The only loop that pays the added group
delay is openpilot's outer loop, outside the EPS. That is a materially better risk profile than the
V287 D-clamp, which sits *inside* the rate loop and changes what the feedback derivative can do — the
route by which rev 1 failed adversary B.
