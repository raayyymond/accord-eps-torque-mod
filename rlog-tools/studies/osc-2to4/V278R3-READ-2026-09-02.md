## 0. Two defects found on the way (EVIDENCE, bytes) — report, not fixed
1. 🛑 **`probe/decode_v278r3_torque_tap.py` decodes the wrong bits.** It uses `((d0&0x7F)<<3)|(d1>>5)` (start bit 7).
   The DBC `MOTOR_TORQUE : 1|10@0+` and the bytes say `((d0&3)<<8)|d1`: byte0 is only ever 0x80/0x82 (CONFIG_VALID +
   the sign bit), byte1 takes 205 values engaged. The kit decoder yields 14 distinct values and |T| ≤ 176 — a false
   "pinned" reading. Every number below uses the DBC layout. `build_v278r3_tva.py` packs `shr 0x1f` → bit 9 = (T<0). ✓
2. 🛑 **Sign convention of DAMP.** The build docstring and the prereg simulation define DAMP against the RAW 0x18F
   rate (bytes 2-3, i16be). The kit decoder negates the wire first ("derived" row). The two are complements.
   Empirical adjudication on this route (EVIDENCE): wire = −7.66·d(ang_0x14A)/dt (r = −0.993); in steady corners
   (|ang|>30, |cmd|>500, n=286) sign(T)=sign(cmd) 100 % and sign(cmd)=−sign(ang_0x14A) 89 %. So T and cmd share a
   convention in which the RAW wire is the wheel's own motion ⇒ "lane opposes the wheel" ⇔ **sign(T) ≠ sign(raw
   wire)** — the build's/prereg's definition. The decoder's "derived" row has the sign backwards (BELIEF: one
   assumption — delivered T acts in the direction the command asks, which the steady-corner 100 % supports).
